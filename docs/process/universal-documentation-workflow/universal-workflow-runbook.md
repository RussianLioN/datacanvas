Проверка: `npm run validate:universal-documentation-workflow`

## Обязательная Последовательность

1. Прочитать `AGENTS.md`.
2. Прочитать `docs/process/universal-documentation-workflow/README.md`.
3. Прочитать `workflow-state.json`, `run-ledger.json`, `event-log.json` и `decision-queue.json`.
4. Прочитать `universal-workflow-core.json`, `datacanvas-profile.json`, `artifact-inventory.json`, `generator-contracts.json` и `validation-command-catalog.json`.
5. Классифицировать запрос: продукт, процесс, архитектура, документация, навигация, generated artifacts или безопасность.
6. Зафиксировать область работ, профиль продукта и `run_id`.
7. Выполнить inventory — инвентаризацию источников, generated artifacts, схем, проверок, видимости и sensitive/confidential data — чувствительных или конфиденциальных данных.
8. Проверить, что универсальные правила берутся из ядра, а DataCanvas-специфика находится только в профиле.
9. Если задача затрагивает Excel backlog, ПШЕ — трудозатраты в человеко-днях, Jira/OPML export или resource estimation — оценку ресурсов, применить Excel-маршрут: raw XLSX не редактировать, working XLSX регистрировать в `docs/product/sources/product-source-registry.json`, фиксировать provenance manifest — манифест происхождения, проверять `npm run validate:xlsx-backlog`, а черновые ПШЕ не переносить как утвержденные без команды реализации.
10. Выполнить impact analysis — анализ влияния — по dependency graph — графу зависимостей.
11. Сформировать decision queue — очередь решений — для блокирующих решений владельцев.
12. Если нужен любой опрос, вопрос или решение владельца по артефакту, перейти в режим `interview_first_deferred_mutation` — сначала интервью, затем пакетная обработка: задать все известные независимые вопросы владельцу и не применять смысловые правки между отдельными ответами.
13. Если следующий вопрос зависит от предыдущего ответа, разбить интервью на короткие раунды; внутри каждого раунда сначала задать все известные вопросы по затронутым артефактам, а записи, генераторы и full gate — полный проверочный барьер — отложить до конца раунда.
14. До завершения интервью или раунда интервью не запускать generated refresh — обновление производных артефактов, hash manifest update — обновление манифеста хэшей, full validation gate — полный проверочный барьер — и финальное validation evidence — проверочные свидетельства. Допустима только минимальная запись состояния для безопасного продолжения после обрыва, без изменения продуктового, процессного, архитектурного, документационного или навигационного смысла.
15. После получения всех ответов интервью применять только явно согласованные правки ручных источников.
16. Если затронуты Vision, BMC, stories, пользовательские истории, бизнес-требования, критерии приемки, product backlog или Confluence export, выполнить очистку business-layer по `business-artifact-content-contract.json`: бизнесовый смысл оставить в Markdown, а технические контракты, source/provenance, проверочные команды, локальные пути, generated metadata и evidence перенести в машинные JSON, process/evidence документы или технические спецификации.
17. Для каждого спорного фрагмента применить матрицу: оставить, переписать, перенести в JSON, оставить как historical evidence вне бизнесового документа или удалить. Если выбор меняет смысл, вернуться к decision queue — очереди решений.
18. Запускать генераторы по generator contracts — контрактам генераторов — и проверять allowed writes — разрешенные записи.
19. После генерации запускать hash check — проверку хэшей — и mutation guard — защиту от лишних изменений.
20. Выполнить quick, profile, generated, security и full gates — быстрый, профильный, generated, security и полный проверочные барьеры — по области изменений, включая `npm run validate:business-docs` для бизнесовых Markdown-артефактов.
21. Если найден новый тип смешения бизнесового и технического слоя, выполнить RCA: симптом, первый загрязненный артефакт, тип смешения, точка первого внесения, причина пропуска предыдущими проверками, contributing factors — сопутствующие причины, preventive artifact — предотвращающий артефакт; затем повторить цикл contract -> cleanup -> generation -> validation.
22. Обновить навигацию через `docs/navigation/navigation-source.json`, затем только генератором обновить generated navigation.
23. Перед завершением проверить отсутствие блокирующих решений, актуальность generated artifacts, связь acceptance records — записей принятия — с правками и наличие следующего безопасного шага.
24. Перед ответом пользователю сначала сформулировать простой итог обычным русским языком. Технические детали, команды, служебные JSON и длинные списки файлов давать отдельным блоком только после простого итога.
25. Если в рабочем чате нужны табличные данные, использовать навык `cli-table-output` или его правила: короткие сравнения давать списком, матрицы и статусные сводки выводить как fenced `text` Unicode-таблицы до 88 видимых символов, Markdown pipe table напрямую в чат по умолчанию не выводить.
26. Если итог, статус, следующий шаг или вопрос упоминает документ, раздел, артефакт или решение, дать абсолютную кликабельную Markdown-ссылку на соответствующий файл в рабочем окружении пользователя. Не заменять ссылку относительным путем, сухим идентификатором или названием документа.
27. Если итог, статус, следующий шаг или вопрос требует решения, правки, проверки спорного текста или объясняет найденную проблему в документе, рядом с абсолютной ссылкой дать короткую цитату релевантного фрагмента.

## Правило Продолжения

После обрыва агент читает `workflow-state.json`, затем `event-log.json`, затем `run-ledger.json`. Продолжение начинается с `current_step`. Если `status` равен `blocked` или `recovery_required`, агент сначала сообщает безопасный следующий шаг из `resume_token` и не применяет правки до восстановления состояния.

## Границы Принятия Решений

- `CO-*` — изменения продукта, `PROC-*` — изменения процесса, и `ADR-*` — архитектурные решения принимаются в разных контурах полномочий.
- Продуктовый смысл берется из Vision — видения, BMC — Business Model Canvas, бизнес-модели продукта, историй, требований, backlog — бэклога, roadmap — дорожной карты, traceability — трассируемости и принятых решений Product Owner.
- Процессный смысл берется из методики, `PROC-*` — изменений процесса, process backlog — процессного бэклога и журналов процесса.
- Архитектурный смысл берется из `ADR-*` — архитектурных решений, схем, контрактов и технических спецификаций.
- Evidence и generated artifacts подтверждают состояние, но не являются первичным источником смысла.

## Матрица Решений От Истории К Требованию

Допустимые решения: создать новое требование, изменить существующее требование, разделить требование, не менять с no-change rationale — обоснованием отсутствия правки, отложить, запросить evidence или признать вход недостаточным для изменения.

No-change rationale должно фиксировать источник, покрытые требования, влияние на acceptance — критерии приемки, влияние на traceability — трассируемость, остаточный риск, владельца, дату и условие повторного рассмотрения.

## Формат Вопроса Владельцу

Если нужно решение владельца, агент не должен ограничиваться ссылкой на `decision queue` — очередь решений — или сухим номером варианта. В рабочем ответе пользователю нужно дать:

- простой смысл вопроса: какое решение нужно и почему без него нельзя продолжать;
- расшифровку каждого кодированного элемента, например `BT-*` — бизнес-требования или `DC-ST-*` — пользовательской истории DataCanvas, и его роль в решении;
- текущий текст каждого элемента, по которому предлагается решение, чтобы пользователь не выбирал вслепую по коду;
- абсолютную ссылку на каждый документ, где есть текст для решения или правки;
- короткую цитату из каждого такого документа;
- документы-доноры или зависимые документы с короткими цитатами, если они используются как основание для варианта;
- логику каждого варианта: что изменится, что останется без изменений и какие риски или блокеры это закрывает;
- варианты решения обычным русским языком, без требования читать JSON;
- рекомендацию агента и объяснение, какие риски она снижает;
- список документов, которые не будут изменены до ответа владельца.

В репозиторных артефактах сохраняются относительные пути; абсолютные кликабельные ссылки используются только в рабочем диалоге, чтобы пользователь быстро открыл нужный файл приложением по умолчанию.

## Формат Отчета Пользователю

Любой отчет после выполнения работы, проверки, остановки или продолжения должен содержать:

- простой итог: что решали, что сделали, где остановились и что требуется от пользователя;
- абсолютные кликабельные ссылки на все документы, которые названы источниками, результатами, открытыми вопросами или следующим шагом;
- короткие цитаты для документов, где требуется решение, правка, проверка спорного текста или объясняется найденная проблема;
- табличные данные в формате `cli-table-output`: список для коротких сравнений или fenced `text` Unicode-таблица для матриц и статусов;
- отдельное техническое дополнение с командами и результатами проверок, если оно помогает проверить работу.

## UX-Френдли Интервью

Когда нужен любой опрос или вопрос по артефакту, агент не должен превращать интервью в цикл "один ответ — правка — генераторы — проверки — следующий вопрос". Такой порядок допустим только при явном запросе пользователя или при критическом риске потери состояния.

Правило одинаково для продуктовых, процессных, архитектурных, навигационных, documentation — документационных, generated artifacts — автоматически создаваемых артефактов, security/evidence — безопасности и проверочных свидетельств — и других артефактов.

Нормальный порядок:

1. Сначала показать пользователю полный набор известных вопросов текущего интервью или текущего раунда.
2. Получить ответы владельца.
3. Сверить, не появились ли новые зависимые вопросы.
4. Если новых вопросов нет, применить согласованные изменения одним пакетом.
5. Затем запустить генераторы, проверки и обновить validation evidence — проверочные свидетельства.

Если часть вопросов условная, агент должен явно сказать: какие вопросы задаются сейчас, какие зависят от ответа, и почему нельзя задать их сразу.

## Завершение

Запуск можно завершить только если:

- открытых блокирующих решений нет;
- все затронутые ручные артефакты обновлены или имеют no-change rationale;
- generated artifacts актуальны и не редактировались вручную;
- hash manifest — манифест хэшей — проходит проверку без записи;
- mutation guard не находит неожиданных изменений;
- acceptance records связаны с решениями и правками;
- run ledger содержит итог, остаточные риски и следующий безопасный шаг.
