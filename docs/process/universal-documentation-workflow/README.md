# Универсальный рабочий процесс проектной документации

Навигация: [DataCanvas](../../../README.md) / [Документация](../../README.md) / [Процесс](../README.md) / Универсальный рабочий процесс документации

Статус: active
Владелец: `Process Owner` — владелец процесса
Проверка: `npm run validate:universal-documentation-workflow`

## Назначение

Пакет задает переносимую методику в домене `documentation_operations` — операциях ведения проектной документации. Методика описывает, как принимать запрос, находить источники истины, анализировать влияние изменений, применять согласованные правки, запускать генераторы и доказывать готовность проверками.

DataCanvas используется только как пилотный профиль ИТ-продукта. Универсальное ядро не содержит продуктовый смысл DataCanvas и не принимает продуктовые, процессные или архитектурные решения вместо владельцев.

Этот документ — основной вход для человека, который хочет запустить или проверить рабочий процесс. [Runbook](universal-workflow-runbook.md) — исполнительная инструкция для агента: в нем перечислены обязательные шаги, правила продолжения после обрыва и критерии завершения запуска.

## Быстрый Старт

Для полного запуска передайте агенту такой запрос:

```text
Запусти универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md.
```

Для продолжения после обрыва используйте:

```text
Продолжи универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md с текущего состояния запуска.
```

В первом ответе агент должен сообщить:

- какие обязательные источники он прочитал;
- как классифицировал запрос: продукт, процесс, архитектура, документация, навигация, generated artifacts — автоматически создаваемые артефакты, или безопасность;
- какой `run_id` — идентификатор запуска — используется или должен быть создан;
- какие источники истины и зависимые артефакты попадают в область влияния;
- какие решения владельцев могут быть нужны до правок;
- какие проверки потребуются для завершения.

Если агент не сообщил эти пункты, попросите его остановиться и сначала выполнить обязательную последовательность из [runbook](universal-workflow-runbook.md).

## Для Кого Эта Инструкция

- Пользователь, который запускает агента, формулирует цель, передает ссылки на артефакты и проверяет, что агент не вышел за согласованную область работ.
- `Process Owner` — владелец процесса — принимает решения о правилах методики, процессных изменениях и маршрутах сопровождения документации.
- `Product Owner` — владелец продукта — принимает решения о продуктовом смысле, требованиях, пользовательских историях и критериях приемки.
- Архитектор или владелец технического решения принимает решения об архитектуре, схемах, контрактах и границах технических интерфейсов.
- Проверяющий смотрит итоговые артефакты, validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг.

## Кто За Что Отвечает

| Участник | Ответственность |
|---|---|
| Пользователь | Описывает цель, объект изменения, ожидаемый результат, известные ограничения и ссылки на исходные артефакты. |
| Агент | Читает обязательные источники, классифицирует запрос, анализирует влияние, предлагает правки, запускает генераторы и проверки. |
| `Process Owner` — владелец процесса | Принимает решения по процессным правилам, `PROC-*` — изменениям процесса, методике и маршрутам сопровождения. |
| `Product Owner` — владелец продукта | Принимает решения по продуктовому смыслу, `CO-*` — изменениям продукта, требованиям, историям и критериям приемки. |
| Архитектор | Принимает решения по `ADR-*` — архитектурным решениям, схемам, контрактам и техническим ограничениям. |

Агент может подготовить формулировку решения, но не принимает смысловое решение вместо владельца.

## Что Позволяет Рабочий Процесс

- Запустить изменение проектной документации от обычного текстового запроса.
- Найти источники истины для продукта, процесса, архитектуры, навигации и проверок.
- Определить ручные артефакты, generated artifacts — автоматически создаваемые артефакты, схемы, evidence — проверочные свидетельства, и проверки, которые затрагивает запрос.
- Сформировать `decision queue` — очередь решений — для вопросов, где агенту нельзя действовать без владельца.
- Применить только явно согласованные изменения в ручных источниках.
- Обновить generated artifacts только через генераторы и проверить, что ручной правки generated artifacts не было.
- Собрать validation evidence — проверочные свидетельства: команды, результаты проверок, ограничения и остаточные риски.
- Продолжить работу после обрыва по `workflow-state.json`, `event-log.json` и `run-ledger.json`.
- Перенести методику на другой ИТ-продукт через профиль продукта, не смешивая универсальные правила с частным смыслом DataCanvas.

## Как Написать Хороший Запрос

Хороший запрос помогает агенту сразу определить область работ и не придумывать смысл за владельца.

В запросе желательно указать:

- цель изменения;
- объект изменения или ссылку на артефакт;
- ожидаемый результат;
- известные ограничения;
- кто должен принять смысловое решение, если оно потребуется;
- запрет на применение смысловых правок без согласования, если задача исследовательская.

Хороший пример:

```text
Запусти универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md для проверки, какие артефакты нужно обновить после изменения правила процесса. Не применяй смысловые правки без решения Process Owner.
```

Хороший пример для анализа без правок:

```text
Проанализируй влияние изменения требования ... через универсальный рабочий процесс. Пока ничего не редактируй: сначала покажи источники истины, затронутые артефакты, решения владельцев и проверки.
```

Слабый пример:

```text
Обнови документацию.
```

Такой запрос слабый, потому что в нем нет цели, объекта изменения, ожидаемого результата, ограничений и владельца решения. Агент должен остановиться, уточнить область работ или сначала провести анализ без правок.

## Что Пользователь Увидит После Запуска

После запуска агент должен коротко показать:

- прочитанные источники;
- классификацию запроса;
- текущий или новый `run_id` — идентификатор запуска;
- область влияния;
- найденные источники истины;
- артефакты, которые нельзя править вручную;
- открытые решения владельцев;
- план действий;
- проверки, которые будут нужны для завершения;
- первый безопасный шаг.

Если запрос уже позволяет действовать, агент может продолжить реализацию. Если запрос меняет смысл продукта, процесса или архитектуры, агент сначала формулирует предлагаемое решение и ждет принятия владельцем.

## Что Агент Делает Сам

- Читает `AGENTS.md`, этот документ, [runbook](universal-workflow-runbook.md), состояние запуска, профиль, инвентарь, контракты генераторов и каталог проверок.
- Классифицирует запрос по домену: продукт, процесс, архитектура, документация, навигация, generated artifacts или безопасность.
- Строит область влияния по источникам, зависимым артефактам, схемам, generated artifacts и проверкам.
- Готовит формулировки решений для владельцев.
- Обновляет только разрешенные ручные источники.
- Запускает генераторы по generator contracts — контрактам генераторов.
- Проверяет allowed writes — разрешенные записи — и отсутствие ручных правок generated artifacts.
- Выполняет релевантные проверки.
- Фиксирует validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг.

## Где Агент Обязан Остановиться

| Ситуация | Почему нужна остановка | Кто принимает решение | Что фиксируется |
|---|---|---|---|
| Меняется продуктовый смысл, требование, история или критерий приемки | Агент не принимает продуктовые решения за владельца продукта. | `Product Owner` — владелец продукта | `decision queue` — очередь решений, `acceptance records` — записи принятия, связь с требованиями или историями. |
| Меняется правило процесса или методики | Процессные правила требуют решения владельца процесса. | `Process Owner` — владелец процесса | `PROC-*` — изменение процесса, запись решения и обновление процессных артефактов. |
| Меняется архитектурное решение, схема или контракт | Технические контракты нельзя выводить из продуктовых документов без архитектурного решения. | Архитектор или владелец технического решения | `ADR-*` — архитектурное решение, схема, контракт или no-change rationale — обоснование отсутствия правки. |
| Источники истины конфликтуют | Нельзя выбирать смысл по догадке. | Владелец соответствующего контура | Описание конфликта, варианты решения и выбранный источник истины. |
| Входных данных недостаточно | Нельзя применять смысловую правку без проверяемого основания. | Пользователь или владелец контура | Запрос недостающих данных или no-change rationale — обоснование отсутствия правки. |
| Нужно изменить generated artifact | Generated artifacts нельзя редактировать вручную. | Обычно решение владельца не требуется; нужен исходный источник и генератор | Исходный ручной артефакт, генератор, allowed writes — разрешенные записи, проверка воспроизводимости. |
| Затронуты sensitive/confidential data — чувствительные или конфиденциальные данные | Нельзя расширять видимость или публиковать данные без явного основания. | Владелец данных или процесса безопасности | Ограничение видимости, redacted metadata — обезличенные метаданные, или отказ от публикации. |
| Нужно расширить доступ, инструменты, публикацию или границы безопасности | Расширение границ доверия требует отдельного решения. | Владелец процесса и владелец безопасности | Решение, rationale — обоснование, проверки безопасности и остаточный риск. |

## Что Рабочий Процесс Не Делает

- Не принимает решения за `Product Owner` — владельца продукта, `Process Owner` — владельца процесса, или архитектора.
- Не выводит продуктовый смысл из `ADR-*` — архитектурных решений, схем, скриптов или generated artifacts.
- Не выводит технический контракт из Vision — видения, BMC — Business Model Canvas, бизнес-модели продукта, историй или требований без архитектурного источника.
- Не редактирует generated artifacts вручную.
- Не ослабляет security validators — проверки безопасности, data-leakage guards — защиты от утечки данных, или tool allowlists — списки разрешенных инструментов.
- Не расширяет network, tools, publish или permission boundaries — сетевые, инструментальные, публикационные или разрешительные границы — без отдельного решения.
- Не смешивает продуктовые задачи DataCanvas с задачами ведения проектной документации, методики, навигации или работы агента.

## Что Будет Результатом Работы

Нормальный результат рабочего процесса включает:

- обновленные ручные артефакты или no-change rationale — обоснование отсутствия правки;
- актуальные generated artifacts, созданные генераторами;
- `decision queue` — очередь решений — без открытых блокирующих вопросов;
- `acceptance records` — записи принятия — связанные с решениями и правками;
- `run ledger` — журнал запуска — с итогом, проверками, остаточными рисками и следующим безопасным шагом;
- `event log` — журнал событий — с ходом работы;
- validation evidence — проверочные свидетельства: команды, результаты и ограничения;
- список проверок, которые были выполнены или осознанно не запускались с объяснением причины.

## Как Понять, Что Работа Завершена

Запуск можно считать завершенным, когда:

- открытых блокирующих решений владельцев нет;
- затронутые ручные артефакты обновлены или имеют no-change rationale — обоснование отсутствия правки;
- generated artifacts актуальны и не редактировались вручную;
- generator contracts — контракты генераторов — соблюдены;
- hash manifest — манифест хэшей — проходит проверку без записи, если изменение затрагивает хэшируемые артефакты;
- mutation guard — защита от лишних изменений — не находит неожиданных правок;
- acceptance records — записи принятия — связаны с решениями и изменениями;
- run ledger — журнал запуска — содержит итог, validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг;
- пользователь понимает, что можно делать дальше: завершить задачу, открыть PR, запросить решение владельца или начать следующий запуск.

## Границы

- Универсальное ядро описывает правила рабочего процесса, но не содержит частные продуктовые утверждения DataCanvas.
- Профиль продукта описывает источники истины, роли, команды и ограничения конкретного ИТ-продукта.
- Экземпляр изменения хранит конкретный `run_id` — идентификатор запуска, область работ, решения владельцев, правки, генерацию, проверки и остаточные риски.
- Product behavior acceptance — принятие изменения поведения продукта, documentation change acceptance — принятие изменения документации, owner decision acceptance — принятие решения владельцем — фиксируются отдельно и не подменяют друг друга.
- Generated artifacts редактируются только через исходный источник и генератор.

## Запуск

Минимальный текстовый запрос:

```text
Запусти универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md.
```

Агент читает runbook, состояние запуска, профиль, инвентарь, очередь решений и журналы. Если правка меняет смысл продукта, процесса или архитектуры, агент формулирует ее как предлагаемое изменение и останавливается до явного принятия владельцем.
