# Универсальный рабочий процесс проектной документации

Навигация: [DataCanvas](../../../README.md) / [Документация](../../README.md) / [Процесс](../README.md) / Универсальный рабочий процесс документации

Статус: active
Владелец: `Process Owner` — владелец процесса
Проверка: `npm run validate:universal-documentation-workflow`

## Назначение

Пакет задает переносимую методику в домене `documentation_operations` — операциях ведения проектной документации. Методика описывает, как принимать запрос, находить источники истины, анализировать влияние изменений, применять согласованные правки, запускать генераторы и доказывать готовность проверками.

DataCanvas используется только как пилотный профиль ИТ-продукта. Универсальное ядро не содержит продуктовый смысл DataCanvas и не принимает продуктовые, процессные или архитектурные решения вместо владельцев.

Этот документ — основной вход для человека, который хочет запустить или проверить рабочий процесс. [Runbook](universal-workflow-runbook.md) — исполнительная инструкция для агента: в нем перечислены обязательные шаги, правила продолжения после обрыва и критерии завершения запуска.

## Быстрый Старт

Для полного запуска передайте агенту такой запрос:

```text
Запусти универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md.
```

Для продолжения после обрыва используйте:

```text
Продолжи универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md с текущего состояния запуска.
```

В первом ответе агент должен сообщить:

- какие обязательные источники он прочитал;
- как классифицировал запрос: продукт, процесс, архитектура, документация, навигация, generated artifacts — автоматически создаваемые артефакты, или безопасность;
- какой `run_id` — идентификатор запуска — используется или должен быть создан;
- какие источники истины и зависимые артефакты попадают в область влияния;
- какие решения владельцев могут быть нужны до правок;
- какие проверки потребуются для завершения.

Если агент не сообщил эти пункты, попросите его остановиться и сначала выполнить обязательную последовательность из [runbook](universal-workflow-runbook.md).

## Для Кого Эта Инструкция

- Пользователь, который запускает агента, формулирует цель, передает ссылки на артефакты и проверяет, что агент не вышел за согласованную область работ.
- `Process Owner` — владелец процесса — принимает решения о правилах методики, процессных изменениях и маршрутах сопровождения документации.
- `Product Owner` — владелец продукта — принимает решения о продуктовом смысле, требованиях, пользовательских историях и критериях приемки.
- Архитектор или владелец технического решения принимает решения об архитектуре, схемах, контрактах и границах технических интерфейсов.
- Проверяющий смотрит итоговые артефакты, validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг.

## Кто За Что Отвечает

| Участник | Ответственность |
|---|---|
| Пользователь | Описывает цель, объект изменения, ожидаемый результат, известные ограничения и ссылки на исходные артефакты. |
| Агент | Читает обязательные источники, классифицирует запрос, анализирует влияние, предлагает правки, запускает генераторы и проверки. |
| `Process Owner` — владелец процесса | Принимает решения по процессным правилам, `PROC-*` — изменениям процесса, методике и маршрутам сопровождения. |
| `Product Owner` — владелец продукта | Принимает решения по продуктовому смыслу, `CO-*` — изменениям продукта, требованиям, историям и критериям приемки. |
| Архитектор | Принимает решения по `ADR-*` — архитектурным решениям, схемам, контрактам и техническим ограничениям. |

Агент может подготовить формулировку решения, но не принимает смысловое решение вместо владельца.

## Что Позволяет Рабочий Процесс

- Запустить изменение проектной документации от обычного текстового запроса.
- Найти источники истины для продукта, процесса, архитектуры, навигации и проверок.
- Определить ручные артефакты, generated artifacts — автоматически создаваемые артефакты, схемы, evidence — проверочные свидетельства, и проверки, которые затрагивает запрос.
- Вести главные артефакты продукта по машинно проверяемой цепочке: принятое продуктовое решение, Vision — видение продукта, BMC — бизнес-модель, пользовательские истории, требования, backlog — бэклог, XLSX-оценка ресурсов, roadmap — дорожная карта, гипотезы, traceability — трассируемость, экспортный пакет и evidence — проверочные свидетельства.
- Провести оценку трудозатрат по рабочему Excel backlog: сохранить raw-источник, подготовить working-копию, проверить точность `.xlsx`-пакета, зафиксировать provenance manifest — машинный манифест происхождения — и не переносить черновые ПШЕ как утвержденные оценки без команды реализации.
- После изменения XLSX или provenance запустить каскадный анализ: каждый downstream-артефакт нужно обновить или закрыть no-change rationale — обоснованием отсутствия правки — в impact analysis, без служебного текста в бизнесовых документах.
- Сформировать `decision queue` — очередь решений — для вопросов, где агенту нельзя действовать без владельца.
- Применить только явно согласованные изменения в ручных источниках.
- Обновить generated artifacts только через генераторы и проверить, что ручной правки generated artifacts не было.
- Собрать validation evidence — проверочные свидетельства: команды, результаты проверок, ограничения и остаточные риски.
- Продолжить работу после обрыва по `workflow-state.json`, `event-log.json` и `run-ledger.json`.
- Перенести методику на другой ИТ-продукт через профиль продукта, не смешивая универсальные правила с частным смыслом DataCanvas.

## Чистота Бизнес-Артефактов

Бизнесовые Markdown-артефакты используются для обсуждения продукта с владельцами и командой. В них остаются только продуктовый смысл, пользовательские сценарии, ценность, требования, критерии приемки, приоритеты, бизнес-границы и открытые решения. Технические контракты, runtime-поля, request/trace/status identifiers — служебные идентификаторы выполнения, команды проверки, хэши, локальные пути, generated metadata — метаданные генерации, Excel/OPML-механика, provenance — происхождение источников, и evidence — проверочные свидетельства — хранятся в машинных JSON, реестрах, технических спецификациях, process/evidence документах или generated-контурах.

Перед очисткой бизнесового документа агент классифицирует каждый спорный фрагмент по матрице: оставить как бизнесовый смысл, переписать простым русским языком, перенести в machine-readable JSON — машинный JSON, оставить как historical evidence — историческое свидетельство вне бизнесового документа, или удалить как служебный дубль. Если выбор меняет смысл продукта, процесса или архитектуры, агент фиксирует вопрос владельцу и останавливается до решения.

Для таких изменений используется gate `npm run validate:business-docs`. Он читает [контракт содержания бизнес-артефактов](business-artifact-content-contract.json) и [контракт генерации бизнес-артефактов](business-artifact-generation-contract.json), дополняет проверки Vision, BMC, source registry, навигации и безопасности и блокирует смешение бизнесового текста с техническими контрактами, проверочными командами, локальными путями, provenance и generated metadata.

Перед очисткой или повторной генерацией бизнес-документа у него должен быть отдельный контракт генерации и блокирующая задача в process backlog. Если такого контракта или задачи нет, сначала фиксируется процессная задача, а документ не перегенерируется и не очищается вручную.

Порядок и каскад главных артефактов дополнительно проверяются через [main artifact lifecycle chain](main-artifact-lifecycle-chain.json) и gate `npm run validate:main-artifact-lifecycle`. Этот contract не хранит продуктовый текст, а задает sequence — последовательность, upstream/downstream связи, owner gates — решения владельцев, и место для no-change rationale — обоснования отсутствия правки — в impact analysis.

## Состав

- [Runbook](universal-workflow-runbook.md) — порядок запуска, продолжения и завершения рабочего процесса.
- [Universal workflow core](universal-workflow-core.json) — переносимые правила, состояния, уровни, проверки и критерии завершения.
- [DataCanvas profile](datacanvas-profile.json) — пилотный профиль проекта документации и ИТ-продукта DataCanvas.
- [Validation command catalog](validation-command-catalog.json) — каталог команд проверки по уровням gate — проверочных барьеров.
- [Artifact inventory](artifact-inventory.json) — инвентарь источников, generated artifacts — автоматически создаваемых артефактов, и evidence — проверочных свидетельств.
- [Generator contracts](generator-contracts.json) — контракты генераторов, разрешенные записи и проверки воспроизводимости.
- [Business artifact generation contract](business-artifact-generation-contract.json) — контракт генерации бизнес-артефактов и блокирующие process backlog задачи для каждого документа, который проверяется `validate:business-docs`.
- [Main artifact lifecycle chain](main-artifact-lifecycle-chain.json) — машинно проверяемый порядок главных артефактов DataCanvas, их каскадные связи, owner gates и профильные проверки.
- [Workflow state](workflow-state.json) — состояние текущего запуска и указатели на журнал, очередь решений и ledger — журнал запуска.
- [Decision queue](decision-queue.json), [decision ledger](decision-ledger.json), [acceptance records](acceptance-records.json), [run ledger](run-ledger.json) и [event log](event-log.json) — контур решений, принятия и событий.
- [Schema coverage registry](schema-coverage-registry.json) — покрытие схемами, положительными примерами и отрицательными сценариями.
- [Mutation guard policy](mutation-guard-policy.json) — защита от лишних изменений и ручной правки generated artifacts.
- [Portability pack](portability-pack.json) — шаблоны переноса методики на другой ИТ-продукт.
- [Product bootstrap pack](product-bootstrap-pack.json) — минимальный стартовый пакет нового ИТ-продукта.

## Как Написать Хороший Запрос

Хороший запрос помогает агенту сразу определить область работ и не придумывать смысл за владельца.

В запросе желательно указать:

- цель изменения;
- объект изменения или ссылку на артефакт;
- ожидаемый результат;
- известные ограничения;
- кто должен принять смысловое решение, если оно потребуется;
- запрет на применение смысловых правок без согласования, если задача исследовательская.

Удобный формат:

```text
Запусти universal workflow для задачи: [что нужно проверить, изменить или подготовить].
Объект: [путь к документу, разделу, требованию, решению или область документации].
Режим: сначала анализ без правок / можно править после найденного источника истины / только проверка готовности.
Ограничения: не менять продуктовый смысл без Product Owner — владельца продукта; не менять процесс без Process Owner — владельца процесса; generated artifacts — автоматически создаваемые артефакты — не редактировать вручную.
Ожидаемый результат: [список артефактов, вопрос владельцу, план правок, выполненные проверки или следующий безопасный шаг].
```

Хороший пример:

```text
Запусти универсальный рабочий процесс проектной документации по docs/process/universal-documentation-workflow/README.md для проверки, какие артефакты нужно обновить после изменения правила процесса. Не применяй смысловые правки без решения Process Owner.
```

Хороший пример для анализа без правок:

```text
Проанализируй влияние изменения требования ... через универсальный рабочий процесс. Пока ничего не редактируй: сначала покажи источники истины, затронутые артефакты, решения владельцев и проверки.
```

Примеры конкретных запросов:

```text
Запусти universal workflow для задачи: проанализировать, какие документы DataCanvas затронет правило, что другой агент после проверки достаточности и безопасности данных сразу запускает подготовку и отправку презентации по электронной почте.
Объект: продуктовые требования, пользовательские истории и acceptance criteria — критерии приемки.
Режим: сначала анализ без правок.
Ограничения: не менять продуктовый смысл без Product Owner — владельца продукта; не менять архитектурные контракты без архитектора; generated artifacts — автоматически создаваемые артефакты — не редактировать вручную.
Ожидаемый результат: источники истины, затронутые артефакты, решения владельцев и проверки.
```

```text
Запусти universal workflow для задачи: найти источник истины для утверждения, что в диалоговом режиме пользователь может сначала посмотреть структуру презентации и только потом запустить изготовление.
Объект: Vision — видение продукта, пользовательские истории, business requirements — бизнес-требования, acceptance criteria — критерии приемки и спецификации.
Режим: только поиск источника истины и анализ влияния, без правок.
Ограничения: не выводить продуктовый смысл из ADR-* — архитектурных решений, schemas — схем или scripts — скриптов.
```

## Что Пользователь Увидит После Запуска

После запуска агент должен коротко показать:

- прочитанные источники;
- классификацию запроса;
- текущий или новый `run_id` — идентификатор запуска;
- область влияния;
- найденные источники истины;
- артефакты, которые нельзя править вручную;
- открытые решения владельцев;
- план действий;
- проверки, которые будут нужны для завершения;
- первый безопасный шаг.

Если запрос уже позволяет действовать, агент может продолжить реализацию. Если запрос меняет смысл продукта, процесса или архитектуры, агент сначала формулирует предлагаемое решение и ждет принятия владельцем.

## Интервью Сначала, Правки Потом

Если нужен любой опрос, вопрос или решение владельца по любому артефакту или контуру полномочий, агент должен работать в режиме `interview_first_deferred_mutation` — сначала интервью, затем пакетная обработка. Правило действует не только для BMC — Business Model Canvas, бизнес-модели продукта, а для продуктовых, процессных, архитектурных, документационных, навигационных, generated artifacts — автоматически создаваемых артефактов, security/evidence — безопасности и проверочных свидетельств — и других артефактов.

Правило по умолчанию:

- сначала собрать полный набор известных независимых вопросов по текущему артефакту, пакету артефактов или раунду решения;
- задать вопросы в чате простым русским языком с абсолютными ссылками, короткими цитатами и готовыми вариантами ответа;
- не обновлять смысловые документы, generated artifacts — автоматически создаваемые артефакты, hash manifest — манифест хэшей — и validation evidence — проверочные свидетельства — между отдельными ответами одного интервью или опросного раунда;
- после получения всех ответов интервью применить согласованные изменения одним пакетом;
- затем запустить генераторы, проверки и обновить evidence.

Если следующий вопрос действительно зависит от предыдущего ответа, интервью разбивается на короткие раунды. Внутри каждого раунда агент все равно сначала задает все известные вопросы по затронутым артефактам, а правки, генерацию и полный gate — проверочный барьер — откладывает до конца раунда.

Минимальная запись состояния допускается только для безопасного продолжения после обрыва: например, зафиксировать, что интервью открыто и какие ответы уже получены. Такая запись не должна менять продуктовый, процессный или архитектурный смысл и не должна запускать тяжелую генерацию вместо продолжения разговора с пользователем.

## Как Агент Сообщает Итоги И Задает Вопросы

Отчет для пользователя должен начинаться с простого человеческого итога: что решали, что сделали, где остановились и что требуется от пользователя дальше. Технические детали, список файлов, команды и служебные идентификаторы нужно выносить в отдельное дополнение после простого итога, только если они помогают проверить работу или продолжить процесс.

Если в рабочем чате нужно показать табличные данные, агент использует навык `cli-table-output` или его правила. Короткие сравнения из 2-4 пунктов лучше давать списком. Матрицы, статусные сводки, scorecard — оценочные таблицы — и псевдографику нужно выводить как fenced `text` блок с Unicode-таблицей шириной до 88 видимых символов. Markdown pipe table не выводится напрямую в чат по умолчанию; он допустим в сохраняемых Markdown-артефактах или по явному запросу пользователя.

Если пользователь просит использовать конкретный навык, плагин, connector — подключенный внешний сервис, MCP-инструмент, Consilium или консилиум экспертов, агент обязан реально вызвать доступный механизм и не имитировать его работу текстом. Если механизм недоступен, не найден или не может быть вызван в текущей среде, это явный блокер: агент сообщает, что именно недоступно, и не выдает имитацию результата.

Любой пользовательский отчет, статус, следующий шаг или вопрос, который ссылается на документ, раздел, артефакт или решение, обязан содержать абсолютную кликабельную Markdown-ссылку на соответствующий файл в рабочем окружении пользователя. Нельзя ограничиваться относительным путем, сухим идентификатором, названием документа или словами "см. файл"; пользователь должен иметь возможность кликнуть ссылку и открыть документ приложением по умолчанию.

Если отчет, статус, следующий шаг или вопрос требует решения, правки, проверки спорного текста или объясняет найденную проблему в документе, рядом с абсолютной ссылкой должна быть короткая цитата релевантного фрагмента. Цитата нужна не вместо ссылки, а как быстрый контекст, чтобы пользователь понимал, почему ему предлагают открыть именно этот документ.

Если агент просит принять решение по документу, вопрос должен содержать:

- короткое объяснение простыми словами, зачем сейчас нужно решение;
- расшифровку каждого кодированного элемента, например `BT-*` — бизнес-требования или `DC-ST-*` — пользовательской истории DataCanvas, рядом с его ролью в решении;
- текущий текст каждого элемента, по которому предлагается решение, чтобы пользователь не выбирал вслепую по коду;
- абсолютную ссылку на каждый документ, по которому требуется решение или правка, в формате рабочего окружения пользователя;
- короткую цитату из релевантного фрагмента документа, который требует решения или правки;
- документы-доноры или зависимые документы с короткими цитатами, если они используются как основание для варианта;
- логику каждого варианта: что изменится, что останется без изменений, какие риски или блокеры это закрывает;
- варианты решения обычным русским языком;
- рекомендацию агента с объяснением, почему она безопасна;
- явное описание, какие документы не будут изменены до ответа владельца.

В сохраняемых артефактах репозитория абсолютные локальные пути не фиксируются: там остаются относительные пути. Абсолютные кликабельные ссылки и цитаты обязательны в рабочем диалоге с пользователем.

## Что Агент Делает Сам

- Читает `AGENTS.md`, этот документ, [runbook](universal-workflow-runbook.md), состояние запуска, профиль, инвентарь, контракты генераторов и каталог проверок.
- Классифицирует запрос по домену: продукт, процесс, архитектура, документация, навигация, generated artifacts или безопасность.
- Строит область влияния по источникам, зависимым артефактам, схемам, generated artifacts и проверкам.
- Готовит формулировки решений для владельцев.
- Если нужен любой опрос, вопрос или решение владельца по артефакту, сначала проводит интервью или короткий раунд интервью, собирает ответы и только затем переходит к правкам, генераторам и проверкам.
- Обновляет только разрешенные ручные источники.
- Запускает генераторы по generator contracts — контрактам генераторов.
- Проверяет allowed writes — разрешенные записи — и отсутствие ручных правок generated artifacts.
- Выполняет релевантные проверки.
- Фиксирует validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг.
- Сообщает итог простым русским языком, а технические детали отделяет от пользовательского решения.

## Где Агент Обязан Остановиться

| Ситуация | Почему нужна остановка | Кто принимает решение | Что фиксируется |
|---|---|---|---|
| Меняется продуктовый смысл, требование, история или критерий приемки | Агент не принимает продуктовые решения за владельца продукта. | `Product Owner` — владелец продукта | `decision queue` — очередь решений, `acceptance records` — записи принятия, связь с требованиями или историями. |
| Меняется правило процесса или методики | Процессные правила требуют решения владельца процесса. | `Process Owner` — владелец процесса | `PROC-*` — изменение процесса, запись решения и обновление процессных артефактов. |
| Меняется архитектурное решение, схема или контракт | Технические контракты нельзя выводить из продуктовых документов без архитектурного решения. | Архитектор или владелец технического решения | `ADR-*` — архитектурное решение, схема, контракт или no-change rationale — обоснование отсутствия правки. |
| Источники истины конфликтуют | Нельзя выбирать смысл по догадке. | Владелец соответствующего контура | Описание конфликта, варианты решения и выбранный источник истины. |
| Входных данных недостаточно | Нельзя применять смысловую правку без проверяемого основания. | Пользователь или владелец контура | Запрос недостающих данных или no-change rationale — обоснование отсутствия правки. |
| Нужно изменить generated artifact | Generated artifacts нельзя редактировать вручную. | Обычно решение владельца не требуется; нужен исходный источник и генератор | Исходный ручной артефакт, генератор, allowed writes — разрешенные записи, проверка воспроизводимости. |
| Затронуты sensitive/confidential data — чувствительные или конфиденциальные данные | Нельзя расширять видимость или публиковать данные без явного основания. | Владелец данных или процесса безопасности | Ограничение видимости, redacted metadata — обезличенные метаданные, или отказ от публикации. |
| Нужно расширить доступ, инструменты, публикацию или границы безопасности | Расширение границ доверия требует отдельного решения. | Владелец процесса и владелец безопасности | Решение, rationale — обоснование, проверки безопасности и остаточный риск. |

## Что Рабочий Процесс Не Делает

- Не принимает решения за `Product Owner` — владельца продукта, `Process Owner` — владельца процесса, или архитектора.
- Не выводит продуктовый смысл из `ADR-*` — архитектурных решений, схем, скриптов или generated artifacts.
- Не выводит технический контракт из Vision — видения, BMC — Business Model Canvas, бизнес-модели продукта, историй или требований без архитектурного источника.
- Не редактирует generated artifacts вручную.
- Не ослабляет security validators — проверки безопасности, data-leakage guards — защиты от утечки данных, или tool allowlists — списки разрешенных инструментов.
- Не расширяет network, tools, publish или permission boundaries — сетевые, инструментальные, публикационные или разрешительные границы — без отдельного решения.
- Не смешивает продуктовые задачи DataCanvas с задачами ведения проектной документации, методики, навигации или работы агента.

## Что Будет Результатом Работы

Нормальный результат рабочего процесса включает:

- обновленные ручные артефакты или no-change rationale — обоснование отсутствия правки;
- актуальные generated artifacts, созданные генераторами;
- `decision queue` — очередь решений — без открытых блокирующих вопросов;
- `acceptance records` — записи принятия — связанные с решениями и правками;
- `run ledger` — журнал запуска — с итогом, проверками, остаточными рисками и следующим безопасным шагом;
- `event log` — журнал событий — с ходом работы;
- validation evidence — проверочные свидетельства: команды, результаты и ограничения;
- список проверок, которые были выполнены или осознанно не запускались с объяснением причины;
- простой пользовательский итог с абсолютными кликабельными ссылками на все документы, которые упоминаются как источники, результаты, открытые вопросы или следующий шаг;
- если нужно решение владельца — вопрос с абсолютными ссылками и цитатами из документов, где требуется решение или правка.

## Как Понять, Что Работа Завершена

Запуск можно считать завершенным, когда:

- открытых блокирующих решений владельцев нет;
- затронутые ручные артефакты обновлены или имеют no-change rationale — обоснование отсутствия правки;
- generated artifacts актуальны и не редактировались вручную;
- generator contracts — контракты генераторов — соблюдены;
- hash manifest — манифест хэшей — проходит проверку без записи, если изменение затрагивает хэшируемые артефакты;
- mutation guard — защита от лишних изменений — не находит неожиданных правок;
- acceptance records — записи принятия — связаны с решениями и изменениями;
- run ledger — журнал запуска — содержит итог, validation evidence — проверочные свидетельства, остаточные риски и следующий безопасный шаг;
- пользователь понимает, что можно делать дальше: завершить задачу, открыть PR, запросить решение владельца или начать следующий запуск.

## Границы

- Универсальное ядро описывает правила рабочего процесса, но не содержит частные продуктовые утверждения DataCanvas.
- Профиль продукта описывает источники истины, роли, команды и ограничения конкретного ИТ-продукта.
- Экземпляр изменения хранит конкретный `run_id` — идентификатор запуска, область работ, решения владельцев, правки, генерацию, проверки и остаточные риски.
- Product behavior acceptance — принятие изменения поведения продукта, documentation change acceptance — принятие изменения документации, owner decision acceptance — принятие решения владельцем — фиксируются отдельно и не подменяют друг друга.
- Generated artifacts редактируются только через исходный источник и генератор.
