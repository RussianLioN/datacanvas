# RCA: свежесть снимка процессных метрик до полной проверки

Навигация: [DataCanvas](../../../README.md) / [Документация](../../README.md) / [База знаний](../README.md) / [RCA](README.md) / Свежесть снимка процессных метрик до полной проверки

Статус: активен

Дата: 2026-08-20

## Проблема

Проверка `docs-check` для PR #25 дважды остановилась в сквозной проверке
`validate:cascade-vnext-e2e`. Временная рабочая копия после полного набора
проверок содержала незакоммиченные производные файлы: снимок процессных метрик
в JSON и Markdown, а также манифест хэшей.

Проверки GitHub: [первый отказ](https://github.com/RussianLioN/datacanvas/actions/runs/32348321445) и [повтор на следующем коммите](https://github.com/RussianLioN/datacanvas/actions/runs/32348854376).

## Факты и воспроизведение

В коммите `b7715a7` в реестр артефактов добавлена запись `ART-883` —
предыдущий RCA о сохранении свидетельств обсуждения. Число записей реестра
стало `883`, а в [снимке метрик](../../process/current/process-metrics-snapshot.json)
осталось `882`.

Генератор [сбора метрик](../../../scripts/collect-process-metrics.mjs) корректно
пересчитывает число записей. Затем [генератор манифеста хэшей](../../../scripts/generate-artifact-hash-manifest.mjs)
пересчитывает хэши изменённых снимков. Строгая проверка чистоты временной
рабочей копии правильно блокирует выпуск: она не является причиной дефекта.

До исправления прямая проверка свежести [`npm run validate:process-metrics-snapshot`](../../../package.json)
для состояния `b7715a7` завершалась сообщением:

```text
ERROR: snapshot count is stale for artifact_registry_entries: expected 883, got 882
```

## Пять почему

1. Почему сквозная проверка завершилась с ошибкой? После генерации в рабочей
   копии остались производные изменения.
2. Почему изменились снимки метрик? Реестр содержал новую запись, а снимки
   ещё отражали прежнее количество.
3. Почему манифест хэшей тоже изменился? Он зависит от содержимого снимков.
4. Почему несоответствие не было показано сразу? Полный набор проверок сначала
   запускал изменяющую генерацию, которая исправляла снимок, и лишь затем
   выполнял проверку свежести.
5. Почему обязательный хвост генерации был пропущен? У генератора снимка не
   было явной записи в договоре генераторов и политике разрешённых изменений,
   поэтому порядок «снимок метрик → манифест хэшей → архив» не был явно
   закреплён рядом с остальными генераторами.

## Корневая причина

Корневая причина — разрыв управляемого порядка генерации после изменения
реестра артефактов. Его усугублял поздний запуск неизменяющей проверки свежести:
полный набор проверок сначала скрывал несоответствие генерацией и сообщал о нём
лишь поздно, как о неочищенной временной рабочей копии.

## Исправление и предотвращение повторения

1. Пересобраны и зафиксированы оба снимка метрик и зависимый манифест хэшей.
2. `npm test` и GitHub Actions теперь запускают
   `npm run validate:process-metrics-snapshot` до `generate:golden`.
3. Регрессионная проверка закрепляет этот порядок в `package.json` и в
   рабочем процессе GitHub.
4. Договор генераторов и политика разрешённых изменений содержат отдельный
   генератор снимка метрик перед генератором манифеста хэшей.
5. Проверка чистоты временной рабочей копии остаётся строгой и продолжает
   находить другие незафиксированные производные результаты.

## Исполняемые проверки

После изменения реестра артефактов порядок обязателен: сначала
`npm run validate:process-metrics-snapshot`, затем генерация снимка метрик,
после неё обновление навигации при необходимости, манифеста хэшей и архива
документации при его изменении.

- `node --test tests/process-metrics-freshness-preflight.test.mjs`;
- `npm run validate:process-metrics-snapshot`;
- `npm run validate:artifact-hashes`;
- `npm run validate:cascade-vnext-e2e`;
- `npm test`;
- `git diff --exit-code`.

## Остаточный риск и правило остановки

Если любая неизменяющая проверка свежести выявляет расхождение, полный набор
проверок, архивирование и отправка ветки не продолжаются. Сначала выполняется
каноническая генерация, в коммит добавляются все фактически изменившиеся
производные файлы, и только затем повторяется полный набор проверок.
