# Технический паспорт пользовательского пути: происхождение, отрисовка и проверки

Навигация: [DataCanvas](../../../../README.md) / [Документация](../../../README.md) / [Продукт](../../README.md) / [Аналитика](../README.md) / [Пользовательский путь заказа и получения презентации](README.md) / Технический паспорт

## Назначение технического паспорта

Документ сохраняет происхождение материалов, внутренние обозначения состояний, устройство визуального пакета, команды генерации и проверочные доказательства. Он не является источником продуктовых требований: подтверждённые положения, решения прототипа и открытые продуктовые вопросы описаны в [человекочитаемом пользовательском пути](user-journey.md) и связанных канонических документах DataCanvas.

## Сжатое время автоматического показа

Надпись «20 минут» остаётся только текстом интерфейса прототипа и не задаёт соглашение о времени готовности. Для проверки поведения автоматический показ сжат до восьми секунд:

1. через 600 миллисекунд после заказа появляется состояние подготовки;
2. до 7,6 секунды поверх телефона работает анимация стрелки часов;
3. на восьмой секунде появляется готовый результат.

При прямом открытии отдельного состояния автоматическая последовательность не запускается.

## Слои и машинные источники пакета

- `source/` — договоры, схемы внутри пакета, происхождение компонентов и шрифт. Два SVG-компонента подключены к принятому HTML: адаптированная [оболочка телефона](source/components/lisa-phone-shell.svg) и созданный для DataCanvas [колокольчик уведомлений](source/components/lisa-notification-bell.svg). [Карточка презентации](source/components/lisa-presentation-card.svg) сохраняется как справочный компонент происхождения и не является отдельным визуальным источником итогового кадра.
- `demo/` — автономная интерактивная демонстрация, созданная из договоров и подтверждённая владельцем; именно принятый HTML является канонической визуальной поверхностью для кадров.
- `derived/` — производные `SVG`- и `PNG`-кадры из браузерных снимков принятого HTML. Они не собираются независимо из справочной карточки и вручную не редактируются.
- `evidence/` — свежие снимки настоящих браузеров, размеры, контрольные суммы и отчёты проверок.

Машинная связность пакета зафиксирована в следующих артефактах:

- [канонический договор состояний](source/journey-contract.json) — 26 состояний, действия и переходы;
- [договор визуального пакета](source/prototype-package-contract.json) — состав исходников, производных файлов, доказательств и команд проверки;
- [манифест производного выпуска](derived/prototype-package-manifest.json) — состав и контрольные суммы актуальных `SVG`- и `PNG`-кадров;
- [отчёт браузерной проверки](evidence/browser-report.json) и [отчёт приёмки](evidence/acceptance-report.json) — доказательства текущей генерации;
- [банк открытых вопросов анализа](../agent-launch-requirements-analysis/question-bank.json) и [состояние анализа требований](../agent-launch-requirements-analysis/analysis-state.json) — машинный контекст нерешённых вопросов, не заменяющий человекочитаемые канонические документы.

## Генерация и проверки

```bash
npm run generate:presentation-link-lisa-user-journey
npm run update:presentation-link-lisa-user-journey:evidence
npm run check:presentation-link-lisa-user-journey
npm run check:presentation-link-lisa-user-journey:evidence
npm run validate:presentation-link-lisa-user-journey
npm run validate:presentation-link-lisa-user-journey:evidence
npm run validate:presentation-link-lisa-user-journey:profile
npm run validate:presentation-link-lisa-user-journey:ci
npm run test:presentation-link-lisa-user-journey:browser
```

`npm run validate:presentation-link-lisa-user-journey:profile` — каноническая локальная проверка выпуска. Она заново создаёт производные кадры и браузерные доказательства в закреплённом окружении, побайтово сравнивает их с сохранённым пакетом и выполняет браузерные проверки. Эту команду запускают при изменении HTML, договоров, генераторов, производных кадров или доказательств.

`npm run validate:presentation-link-lisa-user-journey:ci` — межплатформенная проверка в CI (непрерывной интеграции). Она проверяет свежесть HTML, договоры, целостность сохранённых производных файлов и доказательств, затем заново выполняет функциональные, геометрические проверки и проверки доступности в Chromium и WebKit. Она не пересоздаёт канонические растровые кадры и не требует побайтового совпадения PNG между macOS и Linux: договор прямо устанавливает `cross_platform_png_byte_identity_required: false`. Эта проверка дополняет, но не заменяет каноническую локальную проверку.

Проверка свежести доказательств сначала проверяет сохранённый пакет, затем заново получает 108 снимков Chromium и WebKit во временном каталоге, повторно проверяет их и побайтово сравнивает все 110 файлов с версионируемым пакетом. До и после съёмки она сверяет контрольные суммы входов, поэтому параллельное изменение HTML, договоров или проверочного контура не может дать ложный успешный результат. Временный каталог удаляется как после успеха, так и после ошибки; рабочее дерево не изменяется.

Сначала изменяется канонический договор, затем повторно создаются демонстрация и производные файлы. Перед каждым производным кадром генератор включает технический режим без начальной программной установки фокуса, дожидается загрузки шрифта, восстанавливает нижний якорь только у помеченной прокручиваемой области, снимает случайный программный фокус и пропускает два кадра стабилизации. Обычная интерактивная демонстрация сохраняет перенос фокуса при переходах пользователя. Правило одинаково применяется при создании производных кадров и браузерных доказательств, поэтому загрузка шрифта и перерисовка контура фокуса не меняют кадр между запусками, а экраны без нижнего якоря не прокручиваются. Прямо открытое состояние не запускает автоматическую последовательность, поэтому часы имеют проверяемый режим `static`. Генератор не передаёт Playwright явный параметр служебного стиля для снимка. При этом WebKit внутри Playwright пытается применить собственный встроенный стиль; политика безопасности страницы отклоняет эту попытку, а проверка допускает только точное известное сообщение об этом и завершает работу при любом ином сообщении консоли.

Канонические кадры создаются в WebKit через фиксированный виртуальный адрес `http://lisa.invalid`. Все запросы этого адреса перехватываются Playwright и обслуживаются только файлами переносимого пакета; выхода во внешнюю сеть нет, а выход за каталог пакета блокируется. Chromium остаётся обязательным движком для полного функционального, геометрического и доступностного прогона, WebKit — для канонического кадра и критического междвижкового маршрута. Основной браузерный профиль использует тот же виртуальный адрес, а отдельный тест подтверждает реальное открытие через `file://`. Независимые тесты распределяются между двумя изолированными процессами, чтобы ограничить срок жизни одного процесса WebKit; повторные попытки отключены, а нестабильный результат считается ошибкой. Карточки уведомлений используют обычную сплошную CSS-рамку без зависящей от компоновщика внутренней тени; вторичные кнопки сохраняют внутреннюю линию. Это разделение закреплено визуальным договором и устраняет обнаруженную межпроцессную разницу единичных пикселей карточки. Повторный запуск генератора не должен создавать отличий.

## Вариант 1. Составной вариант

Состав:

- визуальная библиотека `presentation-output/agent-factory-design-package-v1`;
- договоры HTML-оболочки и качества генерации;
- механика прямых состояний и геометрии пакета 016;
- проверочные приёмы активного Kimi v7 `baseline-05`;
- новый центр уведомлений и новая карточка уведомления DataCanvas.

Возможный объём:

- полный дизайнерский пакет — 64 файла, 22 295 066 байт;
- минимальный связный визуальный набор — 46 файлов, 14 100 063 байта;
- полный проверочный контур Kimi — 115 файлов, 30 051 663 байта;
- рекомендуемый буквальный перенос до отдельного подтверждения прав — 0 файлов.

Входы: закреплённые SVG-основы, договоры донора, канонические требования DataCanvas и синтетический сценарий Лисы. Выходы: собственный договор состояний, автономный HTML, производные кадры и новый экран уведомлений.

Для фактического пакета нужны Node.js, Playwright 1.61.1, Axe 4.12.1, opentype.js 2.0.0, установленные браузеры и `rsvg-convert`. Готовая демонстрация работает без сети и сервера.

Пригодность: высокая для чата и высокая для специально созданного центра уведомлений. Требуемая адаптация: заменить устаревший смысл донорских состояний, не переносить предметные данные, отделить текст от контуров SVG, создать доступные HTML-элементы и проверки неизвестного состояния.

Основные риски: закрытый репозиторий без найденной лицензии, неизвестное происхождение части Telegram-SVG, текст в кривых, устаревший продуктовый смысл донорского сценария. Необходимы проверки секретов, относительных путей, ресурсов, геометрии, доступности, прямых ссылок, воспроизводимости и всех отрицательных ветвей.

## Вариант 8. Без копирования

Входы: только канонические документы DataCanvas и подтверждённое владельцем описание пути. Выходы: новый договор, HTML, SVG, PNG и доказательства, созданные в DataCanvas.

Объём донорского копирования — 0 файлов и 0 строк. Зависимости и проверки задаются самим пакетом DataCanvas. Доноры используются только как закреплённые сравнительные источники.

Преимущество — минимальный риск прав и точное соответствие текущему пути. Недостаток — больше самостоятельной визуальной и проверочной работы.

## Решение владельца и фактический перенос

Владелец выбрал вариант 1 и разрешил внутреннее использование выбранных материалов закрытого репозитория, а также техническое исправление указателя навигации. Позднее это общее разрешение было дополнено отдельной директивой владельца: «Возьми из того проекта исходники в виде SVG». В контексте выбранного варианта директива зафиксирована как отдельное разрешение на внутреннюю адаптацию выбранного SVG-исходника. Она не доказывает авторство или права третьих лиц, не заменяет отсутствующую лицензию репозитория и не разрешает внешнее распространение без отдельной правовой проверки.

Затем семантика была уточнена:

- системных push-уведомлений — внешних уведомлений устройства — у Лисы сейчас нет;
- непрочитанное событие обозначается красной точкой возле колокольчика;
- нажатие на колокольчик открывает центр уведомлений;
- готовность одновременно доступна карточкой в чате;
- из чата и уведомления открывается нередактируемая `PDF`-копия;
- действие отправки по электронной почте доступно в просмотрщике и после возврата в чат;
- пользователь получает `PDF` и `PPTX`.

После внесения этих уточнений владелец отдельно подтвердил качество и корректность интерактивного HTML-прототипа и разрешил переход к производным кадрам, доказательствам и документации.

## Проверки, обязательные для выбранного варианта

- схема и связность всех состояний и действий;
- точное прямое открытие `?state=...`;
- контролируемое неизвестное состояние;
- отсутствующий ресурс и повреждённый манифест;
- неверная ссылка уведомления;
- переполнение текста, пересечение рамок и выход за холст;
- маска телефона, минимальные зоны управления и клавиатурный порядок;
- отсутствие внешних запросов, секретов и абсолютных локальных путей;
- отсутствие дублей при повторе одного события готовности;
- отказ уведомления при сохранённой карточке чата;
- недействительная, истёкшая, недоступная и отозванная ссылка;
- отсутствие сети и повтор открытия;
- частичная и полная ошибка почтовой отправки;
- свежие снимки Chromium и WebKit на 1280 × 720, 390 × 844 и 320 × 568;
- повторная генерация без новых отличий.
