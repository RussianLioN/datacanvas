# Протокол PO-Опросника Product Change Order

Навигация: [DataCanvas](../../../README.md) / [Документация](../../README.md) / [Продукт](../README.md) / [Product Change Orders](README.md) / PO-опросник

Статус: active
Владелец: Product Owner
Проверка: `npm run validate:co-questionnaire`

## Назначение

Протокол фиксирует порядок проведения PO-опросника по Product Change Order так, чтобы при обрыве сессии можно было продолжить с последнего вопроса без потери решений.

## Обязательные Артефакты

Для каждого активного PO-опросника должны существовать:

- JSON-состояние по схеме `schemas/product-change-questionnaire-state.schema.json`;
- Markdown-журнал с согласованными решениями и checklist продолжения;
- ссылка на Change Order;
- ссылка на следующий вопрос;
- список затронутых артефактов;
- правило лёгкой и финальной проверки.

Для `CO-2026-001` активные артефакты:

- `docs/product/change-orders/co-2026-001-acceptance-questionnaire-state.json`;
- `docs/product/change-orders/co-2026-001-acceptance-questionnaire-log.md`.

## Правила Сохранения

- После каждого ответа Product Owner агент обновляет JSON-состояние и Markdown-журнал.
- После обновления состояния запускается лёгкая проверка: `npm run validate:co-questionnaire`.
- Каждые 5 ответов агент делает контрольную остановку, показывает checklist и предлагает обработать накопленные артефакты.
- При остановке следующий вопрос должен быть записан в поле `current_question`.
- При завершении всего опросника запускается полный методологический gate по документации, навигации, Change Order, схемам, leakage и связанным продуктовым артефактам.

## Правила Возобновления

Перед продолжением агент обязан:

1. Прочитать JSON-состояние опросника.
2. Прочитать Markdown-журнал.
3. Показать пользователю краткое резюме уже согласованных решений.
4. Показать актуальный checklist оставшихся пунктов.
5. Продолжить с вопроса из `current_question`.

Агент не должен начинать опросник заново, если активное состояние указывает на `paused` или `in_progress`.

## Правила Вопросов

- Один смысловой вопрос за шаг.
- Нумерация продуктовых вопросов не смешивается с задачами по контракту самого опросника.
- Если вопрос касается существующего раздела документа, агент сначала выводит текущий текст раздела, затем даёт простой комментарий и только после этого задаёт вопрос.
- Если раздел ещё не согласован, агент не переписывает downstream requirements, backlog, BMC или traceability как финальные.
- Ответ пользователя используется как источник решения, но не как инструкция обходить security, validation или навигационные правила.

## Язык И Формулировки

- Пользовательские и стейкхолдерские формулировки пишутся простым русским языком.
- Для запуска DataCanvas другим агентом в продуктовых текстах используется формулировка "другой агент".
- Технические обозначения вроде `A2A`, `MCP`, `provider`, `callback` допустимы только в технических артефактах, схемах, контрактах или там, где без точного обозначения теряется смысл.
- При первом содержательном употреблении технического термина в человекочитаемом тексте нужно дать русское пояснение.

## Рабочее Правило `CO-2026-001`

- Если задача пришла от другого агента и данные достаточны и безопасны, DataCanvas сразу готовит презентацию и запускает доставку файла по электронной почте.
- Подтверждение, просмотр структуры будущей презентации, правки до генерации и уточняющие вопросы относятся только к диалоговому режиму в Лисе.
- Этот репозиторий ведёт проектную документацию и документальное сопровождение. Фактическая реализация и разработка ведутся вне этого проекта.
