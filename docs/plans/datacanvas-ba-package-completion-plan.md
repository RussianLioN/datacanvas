# План Формирования Полного BA-Пакета DataCanvas

Навигация: [DataCanvas](../../README.md) / [Документация](../README.md) / [Планы](README.md) / Полный BA-пакет DataCanvas

Статус: draft
Дата: 2026-07-07
Владелец: Product Owner / Process Owner
Проверка: `npm run validate:docs-navigation`, `npm run validate:doc-links`, `npm run validate:universal-documentation-workflow`, `npm run validate:plan-coverage`

## Цель

Сформировать полный, согласованный и проверяемый BA-пакет DataCanvas — пакет бизнес-анализа, который можно использовать для:

- понятного просмотра Product Owner;
- дальнейшего системного анализа;
- подготовки Confluence-ready пакета — набора страниц для переноса в Confluence;
- подготовки Jira/backlog-пакета после проверки Excel, OPML и mapping;
- предварительного планирования работ на 3-4 недельных спринта после оценки трудозатрат командой реализации.

План не меняет продуктовый смысл DataCanvas сам по себе. Все смысловые изменения в Vision, BMC, `DC-ST-*` — пользовательских историях, `BT-*` — бизнес-требованиях, критериях приемки и backlog выполняются только после ответа владельцев.

## Основание

План основан на [аудите трехфазного брейншторма BA-пакета DataCanvas](../process/audits/datacanvas-ba-package-three-phase-brainstorm.md).

Аудит показал, что сначала нужно собрать полный пакет вопросов и решений владельцев, а затем выполнять обновление документов, генерацию производных артефактов и проверки.

## Границы

Входит в план:

- Vision — видение продукта;
- BMC — Business Model Canvas, бизнес-модель продукта;
- `DC-ST-*` — пользовательские истории DataCanvas;
- `BT-*` — бизнес-требования DataCanvas;
- критерии приемки;
- product backlog — продуктовый список работ;
- roadmap — дорожная карта;
- traceability — трассировка;
- BA/SA artifacts — артефакты бизнес- и системного анализа;
- Confluence import map — карта переноса в Confluence;
- Excel, OPML и Jira-цепочка для восстановления источников и импорта;
- generated artifacts — автоматически создаваемые артефакты, которые обновляются только генераторами;
- validation evidence — доказательства проверок.

Не входит в план без отдельного решения:

- назначение численных оценок `ПШЕ` без команды реализации;
- утверждение sprint backlog — списка работ спринта;
- закрытие архитектурного решения callback/status/transport — обратного вызова, статусов и транспорта;
- изменение технических контрактов без ADR — архитектурного решения, schema — схемы данных — или contract artifact — контрактного артефакта;
- ручная правка generated artifacts.

## План Реализации

### 1. Зафиксировать Входное Состояние

1. Проверить текущую ветку, рабочее дерево и статус универсального рабочего процесса.
2. Прочитать источники истины по текущему проходу:
   - Vision;
   - BMC;
   - пользовательские истории;
   - бизнес-требования;
   - backlog;
   - roadmap;
   - traceability;
   - BA/SA artifacts;
   - Confluence import map;
   - Excel/OPML/Jira recovery plan.
3. Отделить продуктовые артефакты от процессных, архитектурных и generated artifacts.
4. Зафиксировать текущие блокеры:
   - нет численных оценок `ПШЕ` для `DC-ST-23` - `DC-ST-28`;
   - не закрыто решение по callback/status/transport;
   - не утверждено, где проходит граница BA-ready — готовности бизнес-анализа — и SA-ready — готовности системного анализа;
   - не завершено решение по Excel -> OPML -> Jira.

### 2. Подготовить Единый Пакет Вопросов

Перед смысловыми правками подготовить один удобный пакет вопросов для владельцев.

Пакет должен:

- идти от самых влияющих решений к менее зависимым;
- показывать, какие ответы могут изменить последующие вопросы;
- давать абсолютные кликабельные ссылки и короткие цитаты спорных фрагментов в рабочем ответе пользователю;
- не предлагать владельцу принимать сырой JSON или технический фрагмент как основной текст вопроса;
- предлагать не менее пяти готовых вариантов формулировки, если согласуется текст документа;
- после ответа обновлять state и журнал опросника.

Вопросы должны покрыть:

1. Состав полного BA-пакета DataCanvas.
2. Готовность BMC после приведения к классическому виду.
3. Готовность Vision после приведения к классическому виду.
4. Разделение маршрута через Лису и маршрута запуска другим агентом.
5. Обработку `DC-ST-23` - `DC-ST-28` — пользовательских историй запуска DataCanvas другим агентом.
6. Оценки `ПШЕ` — трудозатрат из Excel-источника.
7. Границу BA-ready — готовности бизнес-анализа — и SA-ready — готовности системного анализа.
8. Решение по callback/status/transport.
9. Confluence-ready пакет и внутреннее evidence-приложение.
10. Excel -> OPML -> Jira mapping.

### 3. Сформировать Паспорт BA-Пакета

После согласования состава BA-пакета создать или обновить паспорт BA-пакета.

Паспорт должен описывать:

- список обязательных артефактов;
- владельца каждого артефакта;
- источник истины;
- статус готовности;
- зависимые generated artifacts;
- обязательные проверки;
- открытые решения владельцев;
- критерии выхода в системный анализ;
- критерии выхода в планирование спринтов.

Паспорт не должен подменять продуктовые документы. Он только объясняет, как проверить комплектность и готовность.

### 4. Построить Трассировку И Карту Разрывов

Проверить цепочку:

`Vision -> BMC -> DC-ST-* -> BT-* -> критерии приемки -> backlog -> roadmap -> BA/SA artifacts -> specs -> evidence`.

Для каждого разрыва указать:

- где найден разрыв;
- какой источник истины затронут;
- требуется ли решение владельца;
- какие generated artifacts нужно обновить после исправления;
- какие проверки должны подтвердить исправление.

Отдельно проверить:

- что маршрут через Лису не смешан с маршрутом запуска другим агентом;
- что запуск другим агентом после проверки достаточности и безопасности данных идет к подготовке и отправке презентации по электронной почте без подтверждения пользователя;
- что режим Лисы сохраняет диалоговый сценарий со структурой презентации и возможностью правки структуры до генерации;
- что BMC и Vision не содержат служебных разделов, не относящихся к классическому содержанию этих документов.

### 5. Обновить Источники После Ответов Владельцев

После получения ответов внести правки только в ручные источники истины.

Править можно:

- Vision;
- BMC source;
- пользовательские истории;
- бизнес-требования;
- критерии приемки;
- backlog;
- roadmap;
- BA/SA artifacts;
- Confluence import map;
- decision ledger и questionnaire state.

Нельзя вручную править generated artifacts. После правок источников нужно запускать соответствующие генераторы.

### 6. Обновить Generated Artifacts Через Генераторы

После изменения источников запустить генераторы и проверки актуальности:

- BMC package и visual outputs;
- docs navigation;
- artifact registry;
- artifact hash manifest;
- export package;
- traceability outputs;
- PlantUML, SVG и PNG, если они зависят от измененных источников.

Если генератор отсутствует для нужного производного артефакта, сначала зафиксировать это как процессную или техническую задачу, а не редактировать файл вручную.

### 7. Получить Оценки ПШЕ

Для `DC-ST-23` - `DC-ST-28` — пользовательских историй запуска DataCanvas другим агентом — численные оценки `ПШЕ` должны дать команда реализации и Product Owner по подготовленной Excel-матрице.

После получения оценок:

1. Проверить сумму трудозатрат.
2. Проверить емкость команды.
3. Проверить вытеснение уже запланированных работ.
4. Обновить product backlog.
5. Обновить candidate sprint plan — кандидатный план спринтов.
6. Отдельно отметить, какие работы можно брать в ближайший недельный спринт, а какие требуют архитектурного решения или дополнительного анализа.

### 8. Подготовить Confluence И Jira-Пакет

Confluence-ready пакет должен содержать чистые бизнесовые и проектные страницы без служебного мусора:

- Vision;
- BMC;
- пользовательские истории;
- бизнес-требования;
- критерии приемки;
- backlog;
- roadmap;
- traceability overview — обзор трассировки;
- glossary — словарь сокращений и терминов;
- validation summary — краткий итог проверок.

Внутреннее evidence-приложение должно хранить:

- журналы решений;
- state-файлы;
- validation evidence;
- run ledger;
- технические манифесты;
- сведения о generated artifacts.

Jira/OPML-пакет можно считать готовым только после проверки:

- происхождения Excel-источника;
- найденного или восстановленного OPML;
- mapping для Jira;
- отсутствия выдуманных custom fields — настраиваемых полей Jira;
- покрытия `DC-ST-*` и связанных `BT-*`.

### 9. Провести Проверки

Минимальные проверки после процессных и документационных изменений:

- `git diff --check`;
- `npm run generate:docs-navigation -- --check`;
- `npm run validate:docs-navigation`;
- `npm run validate:doc-links`;
- `npm run validate:doc-stale-status`;
- `npm run validate:universal-documentation-workflow`;
- `npm run validate:plan-coverage`;
- `npm run validate:documentation-methodology`;
- `npm run validate:artifact-registry`;
- `npm run validate:artifact-hashes`;
- `npm run scan:secrets`;
- `npm run validate:data-leakage`.

Дополнительные проверки после продуктовых правок:

- `npm run validate:product-vision`;
- `npm run generate:bmc -- --check`;
- `npm run validate:bmc`;
- `npm run validate:ba-sa`;
- `npm run validate:agent-launch-requirements-analysis`;
- `npm run validate:product-sources`;
- `npm run validate:product-source-consistency`;
- `npm test`, если меняются общие контракты, генераторы или несколько созависимых слоев.

### 10. Зафиксировать Итог И Следующие Действия

После проверок нужно:

1. Обновить validation evidence.
2. Зафиксировать открытые решения владельцев.
3. Обновить список generated artifacts.
4. Подготовить простой отчет Product Owner:
   - что изменено;
   - что не менялось;
   - какие решения нужны;
   - какие проверки прошли;
   - какие документы готовы для Confluence;
   - что нужно от команды реализации.
5. Сделать логически отдельные commit и push.

## Критерии Готовности

BA-пакет можно считать готовым к следующему этапу, если:

- все ключевые бизнесовые артефакты согласованы между собой;
- каждая `DC-ST-*` — пользовательская история — связана с `BT-*` — бизнес-требованием — или явно отмечена как открытая;
- у P1-историй есть оценки `ПШЕ` или зафиксирован внешний блокер;
- BMC и Vision соответствуют классическому содержанию своих документов;
- generated artifacts обновлены только генераторами;
- Confluence-ready пакет отделен от внутреннего evidence-приложения;
- открытые архитектурные решения не спрятаны в продуктовых формулировках;
- проверки пройдены и результат зафиксирован.

## Следующий Безопасный Шаг

Продолжить PO-опросник с единого пакета вопросов. До получения ответов не менять продуктовый смысл DataCanvas, не назначать оценки `ПШЕ` и не утверждать sprint backlog.
