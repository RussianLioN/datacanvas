# План каскадного обновления документации CO-2026-003

Навигация: [DataCanvas](../../README.md) / [Документация](../README.md) / [Планы](README.md) / План каскадного обновления документации CO-2026-003

## Назначение

Этот план ведёт завершение документального каскада для `CO-2026-003` — изменения
заказа презентации из Лисы. Он заменяет прежний план пересборки только как
оперативный порядок: исторические записи и результаты не удаляются. Источник
текущего статуса — [реестр разрешений и приёмок выпуска](../product/change-orders/co-2026-003-release-approval-ledger.md).

## Границы

- Принятый черновой прототип содержит 11 кадров. Он является единственным
  согласованным составом для документационного каскада и чернового архива.
- Черновик принят только для документального каскада. Он не разрешает чистовой
  рендер, замену действующей демонстрации, обновление доказательств выпуска или
  архив поставки.
- Кадр письма и три варианта презентации приняты в составе черновика. Их
  повторная приёмка нужна только при изменении источника или состава кадра.
- Для полной недоставки используется тот же принятый кадр и текст, что для
  частичной или неподтверждённой доставки; отдельный текст не создаётся.
- Разрешено публичное размещение согласованных данных демонстрации и визуальных
  производных. Сырые внешние PDF остаются вне Git.

## Порядок выполнения

1. Сверить источники решений, реестр выбранных текстов, текущие требования,
   пользовательские истории, BA/SA, спецификации и трассировку. Каждая правка
   формулировки или формата `PPTX`/`PDF` должна иметь связь с первичным решением.
2. Сверить кандидат маршрута, договор поэкранной подготовки, реестр PDF-доноров
   и реестр приёмок. Проверить единый порядок принятых 11 кадров и разрешённые
   цели доставки `SIGMA`, `OMEGA`, `SIGMA и OMEGA`.
3. Обновить человекочитаемые маршруты: вести к принятому 11-кадровому черновику,
   не продвигать исторический выпуск и не переносить технические детали в
   бизнесовые документы.
4. Устранить корневые причины выпуска: обычная команда прототипа выполняет только
   полный восстанавливаемый выпуск; будущий архив требует итоговую приёмку и один
   отпечаток в реестре, манифесте прототипа и свежих доказательствах.
5. Добавить новые и изменённые документы в карту навигации и реестр артефактов,
   затем штатно пересобрать навигацию, метрики процесса и манифест контрольных
   сумм. Производные файлы редактировать только генераторами.
6. Выполнить узкие проверки контрактов, требований, BA/SA, архивного барьера,
   источников продукта и ссылок. Затем выполнить общий набор проверок и
   подтвердить чистоту рабочей копии после генерации.
7. Зафиксировать независимые по смыслу изменения отдельными коммитами. Публикация
   и проверка точной версии в GitHub допускаются после зелёных локальных проверок.

## Условия следующего визуального этапа

Перед чистовым выпуском владелец отдельно подтверждает итоговый переход к выпуску.
После этого выполняется строгая последовательность: чистовой рендер из согласованных
источников → свежие доказательства с тем же отпечатком кандидата → проверка
прототипа → архив поставки. При изменении источника, договора, генератора или
производного файла последовательность начинается заново с чистового рендера.

## Проверяемые результаты

- Реестр приёмок однозначно показывает, что разрешено сейчас, а что ожидает
  решения владельца.
- Все документы ведут к текущему реестру, а не к историческому доказательству как
  к источнику нового выпуска.
- Обычный запуск не может частично опубликовать HTML, изображения или архив.
- Будущий архив не может быть создан с историческими доказательствами или с
  несовпадающими отпечатками кандидата.
- Навигация и контрольные суммы соответствуют фактически сохранённым документам.
