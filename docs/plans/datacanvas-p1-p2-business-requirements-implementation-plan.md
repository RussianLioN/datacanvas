# План имплементации блица верхнеуровневых бизнес-требований DataCanvas MVP P1-P2

Владелец: Product Owner
Проверка: `git diff --check`

## 1. Цель и результат

Провести экспресс-генерацию верхнеуровневых бизнес-требований DataCanvas для MVP `P1-P2` и подготовить материал, пригодный для переноса в `docs/product/requirements/business-requirements.md`.

Результат блица:

- сохранены существующие `BT-001..BT-004`;
- добавлены новые требования `BT-005..BT-014`;
- каждое новое `BT-*` связано с `DC-ST-01..DC-ST-09`, Vision/BMC и проверяемым acceptance-сценарием;
- открытые продуктовые решения не выдаются за подтвержденные факты;
- security/trust boundaries подняты на уровень бизнес-требований;
- P3-P5 возможности явно исключены из MVP P1-P2.

## 2. Исходные решения блица

Использовать следующие рабочие решения как assumptions, а не как уже утвержденные repo facts:

| Область | Решение блица | Как фиксировать |
|---|---|---|
| Первичный пользователь | КМ | Основной пользователь MVP |
| Главная ценность | Снижение ручной работы | Критерий успеха и rationale |
| Scope | `DC-ST-01..DC-ST-09` | Только P1-P2 |
| Согласование | Обязательное описание до генерации | Business rule для MVP |
| Export default | `PPTX` и `PDF` | Product decision для фиксации |
| Доставка | Рабочая почта КМ | Product decision для фиксации |
| Security | Все входы недоверенные | Business constraint |

Не включать в P1-P2:

- выбор сообщений в Лисе;
- кнопку `Сделать презентацию`;
- push-уведомления;
- диаграммы;
- несколько вариантов оформления;
- просмотр в Лисе;
- post-delivery правки через агента или ответное письмо.

## 3. Обновленный набор BT v0.2

Существующие требования сохраняются без перенумерации:

| ID | Требование | Действие |
|---|---|---|
| BT-001 | DataCanvas принимает структурированный пакет данных от другого агента | Сохранить, уточнить источники при необходимости |
| BT-002 | DataCanvas генерирует краткую презентацию, пригодную для проверки человеком | Сохранить |
| BT-003 | Каждый значимый claim должен трассироваться к источнику | Сохранить |
| BT-004 | Итоговый export не должен содержать служебные данные, raw traces или секреты | Сохранить и связать с broader security |

Новые требования:

| ID | Бизнес-требование | Источник | Acceptance / evidence |
|---|---|---|---|
| BT-005 | DataCanvas должен позволять КМ запускать подготовку презентации из Лисы после диалога с другими агентами или в начале сессии, чтобы не переносить данные вручную. | DC-ST-05, DC-ST-07, Vision | Сценарии запуска из двух P2 контуров описаны и связаны с входным контекстом. |
| BT-006 | DataCanvas должен принимать входной контекст только как недоверенные данные, проводить проверку, классификацию и нормализацию до дальнейшей обработки. | BT-001, Vision, trust boundaries | Невалидный, секретный или неклассифицированный вход не идет в генерацию. |
| BT-007 | Если входных данных недостаточно, DataCanvas должен задавать КМ уточняющие вопросы в Лисе и не генерировать неполный результат. | DC-ST-06, Vision, BMC | Есть positive/negative сценарий: достаточный вход идет дальше, недостаточный останавливается на уточнении. |
| BT-008 | DataCanvas должен формировать описание будущей презентации по слайдам, блокам, данным, порядку и ожидаемому виду результата. | DC-ST-01, Vision | Описание можно проверить человеком до генерации. |
| BT-009 | DataCanvas должен требовать согласования описания презентации КМ до генерации файла. | Vision, BMC | Без согласования файл не генерируется. |
| BT-010 | КМ должен иметь возможность править описание до генерации: дополнять блоки, менять расположение блоков и удалять лишнюю информацию. | DC-ST-02, DC-ST-03, DC-ST-04 | Все три действия покрыты; бизнес-ценность `DC-ST-03/04` помечена как требующая уточнения, не дописывается. |
| BT-011 | DataCanvas должен позволять КМ выбрать формат и шаблон из предложенных вариантов, чтобы снизить ручную настройку оформления. | DC-ST-08, BMC | Формат/шаблон выбран до генерации; каталог шаблонов остается open decision. |
| BT-012 | DataCanvas должен генерировать согласованный export и доставлять его по электронной почте в рамках MVP. | BT-002, DC-ST-09, Vision | Файл создан и отправлен; `PPTX/PDF` и правило адресата фиксируются как blitz assumptions. |
| BT-013 | DataCanvas должен защищать prompt, trace, evidence, runtime state, email и export от prompt injection, секретов, PII, raw traces, internal prompts и tool outputs. | BT-004, security docs, threat model | Stop rule срабатывает при unsafe input/output; evidence не содержит raw confidential data. |
| BT-014 | DataCanvas должен сохранять связь между запросом, входным контекстом, описанием, согласованием, export и статусом доставки. | Vision, BMC, DoR/DoD | Есть lifecycle trace: request -> input -> description -> approval -> export -> delivery status. |

## 5. Acceptance-сценарии

Проверить минимум следующие сценарии:

| Сценарий | Ожидаемый результат |
|---|---|
| Happy path | КМ запускает DataCanvas, вход достаточен, описание согласовано, export доставлен. |
| Insufficient input | DataCanvas задает уточняющие вопросы и не генерирует файл. |
| Edit before generation | КМ дополняет, перемещает или удаляет блоки до генерации. |
| Format/template selection | КМ выбирает формат и шаблон из предложенных вариантов. |
| Email delivery | Export отправлен по email, статус доставки зафиксирован. |
| Unsupported claim | Неподтвержденный claim уточняется или исключается. |
| Conflicting sources | Конфликтующие данные не попадают в финальный claim без разрешения. |
| Prompt injection | Инструкции из входного текста, agent output или вложений не меняют правила DataCanvas. |
| Secret/PII leakage | Секреты и PII не попадают в prompt, trace, evidence, email или export. |
| P3-P5 guard | В BT P1-P2 не появляются push, просмотр в Лисе, диаграммы, кнопка и post-delivery repair. |

## 6. Implementation Steps

1. Зафиксировать source inventory: `business-requirements.md`, `product-vision.md`, `vision-v0.1.md`, `stories.md`, BMC v0.2, acceptance criteria, NFR, trust boundaries, data classification, threat model.
2. Обновить `business-requirements.md` до v0.2 без перенумерации `BT-001..BT-004`.
3. Добавить `BT-005..BT-014` в едином формате: capability, user/stakeholder, value, source, status.
4. Добавить таблицу покрытия `DC-ST-01..DC-ST-09 -> BT-*`.
5. Добавить раздел assumptions/open decisions: `PPTX/PDF`, рабочая почта КМ, правила адресата, каталог шаблонов.
6. Обновить traceability matrix для новых `BT-*`, не ломая существующие ссылки на `BT-001` и `BT-003`.
7. Связать новые BT с acceptance-сценариями и evidence expectations.
8. Проверить, что `BT-014` закрывает lifecycle trace, а метрики снижения ручной работы вынесены в success metrics.
9. Проверить security wording: входы как данные, data classification, prompt injection, redacted evidence, безопасная email-доставка.
10. Проверить отсутствие P3-P5 leakage.

## 7. Validation Gate

Готово, когда выполнены все условия:

- нет collision или переопределения `BT-001..BT-004`;
- `DC-ST-01..DC-ST-09` покрыты на 100%;
- каждый новый `BT-*` имеет source, status, acceptance scenario и evidence expectation;
- `PPTX/PDF` и рабочая почта КМ отмечены как blitz assumptions/product decisions;
- `DC-ST-03/04` не получают выдуманную бизнес-ценность;
- security покрывает input, prompt, trace, evidence, runtime state, email и export;
- P3-P5 возможности отсутствуют в MVP P1-P2;
- после переноса в файлы проходят `git diff --check`, профильные docs/requirements проверки и security/data-leakage проверки, если они доступны в текущем `package.json`.

## 8. Assumptions

- `БТ` означает бизнес-требования.
- Все новые требования имеют статус `draft`.
- Блиц не утверждает финальный технический контракт входного пакета.
- Блиц не утверждает каталог шаблонов, владельцев шаблонов и правила обновления.
- Блиц не утверждает полный post-delivery repair loop.
- Основной пользователь MVP: КМ.
- Главный эффект MVP: снижение ручного выбора, копирования, структурирования и оформления данных.
