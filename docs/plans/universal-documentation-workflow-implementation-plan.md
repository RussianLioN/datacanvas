# План Универсального Рабочего Процесса Валидации, Правки И Генерации Артефактов Проектной Документации

Навигация: [DataCanvas](../../README.md) / [Документация](../README.md) / [Планы](README.md) / Универсальный рабочий процесс документации

Статус: draft
Владелец: Process Owner
Проверка: `npm run validate:docs-navigation`, `npm run validate:artifact-registry`, `npm run validate:artifact-hashes`

## Назначение

План описывает реализацию переносимого workflow — рабочего процесса — для валидации, правки и генерации артефактов проектной документации любого ИТ-продукта.

DataCanvas в этом плане используется как пилотный ИТ-продукт и профиль применения методики. Универсальная методика должна оставаться отчуждаемой: ее можно перенести на другой ИТ-продукт без копирования продуктовых смыслов DataCanvas, частных change orders — заявок на изменение, спринтов, релизов, ролей, терминов и проверок.

## 1. Сформировать Универсальное Ядро И Профиль DataCanvas

1. Создать отдельный переносимый пакет методики для работы с проектной документацией любого ИТ-продукта.
   - Универсальное ядро не должно содержать DataCanvas-термины, `CO-2026-001` — принятое изменение приоритета запуска DataCanvas другим агентом, BMC — Business Model Canvas, бизнес-модель продукта — DataCanvas, Лису, конкретные спринты, релизы, провайдеров или частные пути продукта.
   - DataCanvas оформить как пилотный профиль, который подключает универсальную методику к текущему репозиторию.

2. Разделить артефакты на три уровня.
   - Универсальное ядро: правила, состояния, проверки, шаблоны, контракты генераторов, порядок запуска, критерии завершения.
   - Профиль продукта: название ИТ-продукта, доменная структура, источники истины, роли, владельцы, артефакты, команды проверки, правила видимости и безопасности.
   - Экземпляр изменения: конкретная заявка, пакет ревизии, решение владельца, правки, сгенерированные артефакты, evidence — проверочные свидетельства.

3. Добавить профильные структуры.
   - `project_profile` — профиль проекта ведения документации: роли, владельцы, маршруты, правила навигации, команды проверки, правила языка, контур безопасности.
   - `product_profile` — профиль ИТ-продукта: Vision — видение, цели, стейкхолдеры, источники продуктового смысла, бизнес-требования, пользовательские истории, системные требования, backlog — бэклог, roadmap — дорожная карта, traceability — трассируемость.
   - `validation_command_catalog` — каталог команд проверки: какие проверки относятся к ядру, профилю, DataCanvas-пилоту, безопасности, generated artifacts — автоматически создаваемым артефактам — и полному gate — проверочному барьеру.

4. Обобщить текущие DataCanvas-пакеты.
   - Пакет ревизии `CO-2026-001` — принятое изменение приоритета запуска DataCanvas другим агентом — превратить в шаблон artifact revision package — пакета ревизии артефактов.
   - Prompt-only пакет оставить как интерфейс запуска, но не как всю методику.
   - BMC — Business Model Canvas, бизнес-модель продукта — вынести из универсального ядра в профиль продукта.

## 2. Усилить Источники Истины, Полномочия И Навигацию

1. Зафиксировать правило двух доменов навигации.
   - `product` — продуктовая документация конкретного ИТ-продукта.
   - `documentation_operations` — методика, рабочий процесс, проверки, планы, схемы, генераторы и управление проектной документацией.
   - Продуктовый смысл нельзя выводить из планов, `PROC-*` — изменений процесса, `ADR-*` — архитектурных решений, схем, скриптов, generated artifacts — автоматически создаваемых артефактов — или evidence — проверочных свидетельств — как из первичного источника.

2. Добавить переносимые навигационные признаки.
   - `universal` — относится к универсальной методике.
   - `pilot_specific` — относится к пилоту DataCanvas.
   - `project_specific` — относится к конкретному ИТ-продукту.
   - `generated` — автоматически создаваемый артефакт.
   - `sensitive_metadata_only` — в публичной навигации допустимы только обезличенные метаданные.

3. Добавить или уточнить навигационные маршруты.
   - `role-documentation-architect` — архитектор документации и методики.
   - `task-start-documentation-workflow` — запуск полного рабочего процесса по артефактам документации.
   - `task-port-documentation-workflow` — перенос методики на другой ИТ-продукт.
   - `task-review-change-impact` — анализ влияния изменения на артефакты.
   - `task-find-source-of-truth-by-decision-type` — поиск источника истины по типу решения.
   - DataCanvas-маршруты оставить как пилотные примеры, а не как универсальные входы.

4. Обновить навигационные документы через источник истины.
   - Ручные изменения вносить только в `docs/navigation/navigation-source.json`.
   - Generated navigation files — автоматически создаваемые навигационные файлы — обновлять только генератором.
   - Все новые документы включать в навигацию или в `ignored_paths` с причиной.
   - Для каждого входного маршрута указывать домен, группу, владельца, стартовый путь, следующие пути, видимость, класс данных, режим поиска и проверочную команду.

5. Обновить обзорные документы.
   - В корневом `README.md` и `docs/README.md` явно отделить DataCanvas как продукт от универсальной методики ведения документации.
   - В `docs/process/README.md` добавить маршрут запуска универсального рабочего процесса.
   - В `docs/project-map.md` добавить слой “универсальная методика / профиль DataCanvas / экземпляр изменения”.

## 3. Ввести Универсальную Модель Запуска И Состояния

1. Описать `UniversalDocumentationWorkflowState` — универсальное состояние рабочего процесса.
   - `workflow_id`
   - `workflow_version`
   - `project_profile_id`
   - `product_profile_id`
   - `run_id`
   - `status`
   - `phase`
   - `current_step`
   - `scope`
   - `artifact_catalog_path`
   - `decision_queue_path`
   - `event_log_path`
   - `run_ledger_path`
   - `validation_plan`
   - `resume_token`

2. Разделить состояние запуска и состояние сессии.
   - Run state — состояние конкретного запуска: вход, область работ, хэши до запуска, решения, правки, генерация, проверки, итог.
   - Session state — состояние текущего диалога или агентского выполнения: последний безопасный шаг, открытые вопросы, режим продолжения.
   - Активный запуск должен иметь указатель на текущий `run_id`.

3. Ввести машину состояний.
   - `initialized` — запуск создан.
   - `intake_validated` — входной запрос проверен.
   - `inventory_completed` — инвентаризация артефактов завершена.
   - `methodology_checked` — методика и профиль проверены.
   - `impact_analyzed` — влияние изменений проанализировано.
   - `awaiting_decision` — требуется решение владельца.
   - `approved_to_apply` — правки разрешены.
   - `applying_changes` — правки применяются.
   - `generating` — generated artifacts — автоматически создаваемые артефакты — создаются заново.
   - `validating` — проверки выполняются.
   - `blocked` — выполнение заблокировано.
   - `recovery_required` — требуется восстановление после сбоя.
   - `completed` — запуск завершен.
   - `abandoned` — запуск прекращен.

4. Ввести транзакционный run ledger — журнал запуска.
   - Фиксировать входной запрос, режим, область работ, начальные хэши, найденные источники, решения, примененные правки, пропущенные правки, generated outputs — автоматически созданные выходные артефакты, команды проверки, результаты, остаточные риски и следующий безопасный шаг.
   - Все значимые переходы состояния писать в append-only event log — журнал событий только с добавлением записей.

5. Ввести универсальные записи принятия решений.
   - Owner decision acceptance — принятие решения владельцем.
   - Documentation change acceptance — принятие изменения документации.
   - Product behavior acceptance — принятие изменения поведения продукта.
   - `CO-*` — изменения продукта, `PROC-*` — изменения процесса, и `ADR-*` — архитектурные решения должны приниматься отдельно и не подменять друг друга.

## 4. Формализовать Инвентаризацию, Зависимости И Каскадные Правки

1. Создать единый artifact inventory — инвентарь артефактов.
   - Согласовать artifact link catalog — каталог ссылок на артефакты, navigation source — источник навигации, artifact registry — реестр артефактов, hash manifest — манифест хэшей, и leakage manifest — манифест контроля утечек — через единые идентификаторы и cross-checks — перекрестные проверки.
   - Для каждого артефакта хранить тип, владельца, домен, профиль, источник истины, generated/manual статус, чувствительность, входы, выходы и команды проверки.

2. Ввести authority taxonomy — таксономию полномочий источников.
   - Продуктовый смысл: Vision — видение, BMC — Business Model Canvas, бизнес-модель продукта, пользовательские истории, требования, backlog — бэклог, roadmap — дорожная карта, traceability — трассируемость, принятые решения владельца продукта.
   - Процесс: методика, `PROC-*` — изменения процесса, process backlog — процессный бэклог, журналы процесса.
   - Архитектура: `ADR-*` — архитектурные решения, схемы, контракты, технические спецификации.
   - Evidence — проверочные свидетельства: результаты проверок, выгрузки, отчеты, журналы, сгенерированные подтверждения.
   - Generated artifacts — автоматически создаваемые артефакты — не могут быть первичным источником смысла.

3. Ввести dependency graph — граф зависимостей.
   - Смысловые правки должны проходить impact analysis — анализ влияния.
   - Граф должен находить downstream artifacts — зависимые артефакты, циклы, отсутствующие узлы, блокирующие решения и требуемую регенерацию.
   - Автоматическое применение смысловых каскадных правок оставить opt-in — включаемым только по явному решению — до отдельного принятого процессного решения.

4. Ввести матрицу решений для перехода от истории к требованию.
   - Создать новое требование.
   - Изменить существующее требование.
   - Разделить требование.
   - Не менять с no-change rationale — обоснованием отсутствия правки.
   - Отложить.
   - Запросить evidence — проверочное свидетельство.
   - Признать недостаточным для изменения.

5. Ввести стандарт no-change rationale — обоснования отсутствия правки.
   - Источник.
   - Покрытые требования.
   - Влияние на acceptance — критерии приемки.
   - Влияние на traceability — трассируемость.
   - Остаточный риск.
   - Владелец.
   - Дата.
   - Условие повторного рассмотрения.

## 5. Усилить Генераторы, Хэши И Проверки Воспроизводимости

1. Ввести `generator contract` — контракт генератора — для каждого генератора.
   - Inputs — входы.
   - Outputs — выходы.
   - Allowed writes — разрешенные записи.
   - `generate_command`
   - `check_command`
   - Deterministic environment — воспроизводимое окружение.
   - Dependencies — зависимости.
   - Post-validators — проверки после генерации.
   - Owner — владелец.
   - Failure modes — режимы отказа.

2. Добавить `--check` для hash manifest — манифеста хэшей.
   - `generate-artifact-hash-manifest` должен уметь проверять актуальность без записи.
   - Этот режим должен запускаться после всех генераторов.
   - Расхождение должно давать понятную диагностику и команду исправления.

3. Ввести `mutation guard` — защиту от лишних изменений.
   - Перед генерацией фиксировать ожидаемые outputs — выходные артефакты.
   - После генерации проверять, что изменились только разрешенные файлы.
   - Ручная правка generated artifacts — автоматически создаваемых артефактов — должна блокировать завершение.

4. Ввести topological planner — планировщик порядка правок.
   - Строить порядок обновления по dependency graph — графу зависимостей.
   - До правок выявлять циклы, отсутствующие зависимости, устаревшие generated artifacts — автоматически создаваемые артефакты — и блокирующие решения.
   - Для каждого шага указывать источник, зависимые артефакты, генератор и проверку.

5. Ввести drift diagnosis — диагностику расхождений.
   - Объяснять, почему артефакт устарел.
   - Показывать изменившийся источник.
   - Показывать команду исправления.
   - Разделять расхождение от ручной правки, устаревшей генерации и изменения профиля.

6. Ввести многоуровневые gates — проверочные барьеры.
   - Quick gate — быстрые проверки структуры и схем.
   - Profile gate — проверки профиля продукта.
   - Generated gate — генераторы, `--check`, хэши и mutation guard — защита от лишних изменений.
   - Security gate — проверка безопасности, секретов, утечек данных, видимости и классов данных.
   - Full gate — полный набор проверок перед завершением или передачей.

   - Шаблон hash manifest — манифеста хэшей.
   - Шаблон leakage manifest — манифеста контроля утечек.
   - Шаблон workflow state — состояния рабочего процесса.
   - Шаблон decision queue — очереди решений.
   - Шаблон acceptance record — записи принятия.
   - Шаблон run ledger — журнала запуска.
   - Шаблон migration notes — заметок по переносу.

2. Добавить product bootstrap pack — стартовый пакет продукта.
   - Vision — видение.
   - Цели продукта.
   - Стейкхолдеры.
   - BRD — документ бизнес-требований.
   - SRS — документ системных требований.
   - Backlog — бэклог.
   - Risks — риски.
   - Acceptance — приемка.
   - Traceability — трассируемость.
   - Release/evidence — релизные и проверочные свидетельства.

3. Добавить нейтральные фикстуры вне DataCanvas.

   - Положительный сценарий успешного запуска методики.

4. Ввести фазы внедрения на новом ИТ-продукте.
   - Bootstrap — создание профиля и минимальных источников.
   - Advisory scan — рекомендательная проверка без блокировки.
   - Fix pass — исправление навигации, схем, индексов и generated artifacts — автоматически создаваемых артефактов.
   - Strict rollout — включение блокирующих проверок.
   - Pilot feedback gate — проверочный барьер обратной связи пилота перед закреплением методики.

1. Добавить или расширить JSON Schema — схемы данных — для универсальных сущностей.
   - `project_profile`
   - `product_profile`
   - `artifact_inventory`
   - `validation_command_catalog`
   - `workflow_state`
   - `decision_queue`
   - `decision_ledger`
   - `acceptance_record`
   - `run_ledger`
   - `event_log`
   - `generator_contract`
   - `schema_coverage_registry`

2. Разделить команды проверки.
   - `validate:documentation-core` — универсальные инварианты методики.
   - `validate:documentation-profile` — профиль продукта и проекта.
   - `validate:datacanvas-profile` — DataCanvas-пилот.
   - `validate:workflow-state-ledger` — состояние, журнал запуска, очередь решений и принятия.
   - `validate:generator-contracts` — контракты генераторов.
   - `validate:schema-coverage` — покрытие схемами и фикстурами.
   - `validate:mutation-guard` — лишние изменения и ручные правки generated artifacts — автоматически создаваемых артефактов.
   - `validate:universal-documentation-workflow` — сводный профильный gate — проверочный барьер.

3. Проверить schema coverage — покрытие схемами.
   - Каждый JSON/YAML-артефакт должен иметь схему.
   - Для каждой схемы нужен positive fixture — корректный пример.
   - Для рискованных схем нужен negative fixture — некорректный пример.
   - Если negative fixture не нужен, требуется `not_applicable` rationale — обоснование неприменимости.

4. Усилить security/leakage pack — пакет безопасности и контроля утечек.
   - Любой новый prompt — запрос, trace — трасса, export — экспорт, evidence — проверочное свидетельство или runtime sink — место записи во время выполнения — должен иметь data class — класс данных.
   - Публичная навигация не должна раскрывать confidential/sensitive data — конфиденциальные или чувствительные данные.
   - Исключения должны иметь владельца, причину и срок пересмотра.

## 8. Зафиксировать Порядок Полного Запуска Рабочего Процесса

1. Intake — прием запроса.
   - Определить, относится запрос к продукту, процессу, архитектуре, документации, навигации, generated artifacts — автоматически создаваемым артефактам — или безопасности.
   - Зафиксировать область работ, режим запуска и профиль продукта.
   - Создать `run_id`.

2. Inventory — инвентаризация.
   - Найти ручные источники.
   - Найти generated artifacts — автоматически создаваемые артефакты.
   - Найти навигационные входы.
   - Найти схемы, проверки, registry — реестр, и hash coverage — покрытие хэшами.
   - Найти чувствительные данные и ограничения публикации.

3. Methodology check — проверка методики.
   - Убедиться, что правила применяются из универсального ядра.
   - Убедиться, что DataCanvas-специфика находится в профиле.
   - Проверить, что продуктовые решения не смешаны с процессными и архитектурными.

4. Impact analysis — анализ влияния.
   - Построить dependency graph — граф зависимостей.
   - Сформировать список артефактов к правке.
   - Сформировать список generated artifacts — автоматически создаваемых артефактов — к пересозданию.
   - Сформировать decision queue — очередь решений — для блокирующих решений.

5. Decision pass — проход принятия решений.
   - Для смысловых изменений требовать acceptance record — запись принятия.
   - Для спорных или недостаточных данных блокировать применение.
   - Для no-change — решения не менять — фиксировать rationale — обоснование.

6. Apply pass — проход применения правок.
   - Править только ручные источники.
   - Generated artifacts — автоматически создаваемые артефакты — не редактировать вручную.
   - Соблюдать владельцев, домены и классы данных.

7. Generate pass — проход генерации.
   - Запускать генераторы по topological planner — планировщику порядка правок.
   - Использовать `--check` там, где запись не требуется.
   - После записи запускать mutation guard — защиту от лишних изменений — и hash check — проверку хэшей.

8. Validate pass — проход проверки.
   - Запустить quick/profile/generated/security/full gates — быстрый, профильный, generated, security и полный проверочные барьеры — по области изменений.
   - Сохранить validation evidence — проверочные свидетельства.
   - Блокировать завершение при незакрытых ошибках.

9. Index pass — проход индексации.
   - Обновлять `navigation-source.json` вручную.
   - Generated navigation — автоматически создаваемую навигацию — обновлять генератором.
   - Проверять links — ссылки, navigation contract — навигационный контракт, stale status — устаревшие статусы, registry — реестр и hash manifest — манифест хэшей.

10. Completion pass — проход завершения.
   - Проверить отсутствие блокирующих решений.
   - Проверить, что все затронутые ручные артефакты обновлены или имеют no-change rationale — обоснование отсутствия правки.
   - Проверить, что generated artifacts — автоматически создаваемые артефакты — актуальны.
   - Проверить, что acceptance records — записи принятия — связаны с правками.
   - Зафиксировать итоговый статус, остаточные риски и следующий безопасный шаг.

## 9. Проверки И Критерии Приемки Реализации

1. Минимальные проверки после реализации.
   - `npm run validate:schemas`
   - `npm run generate:docs-navigation -- --check`
   - `npm run validate:doc-links`
   - `npm run validate:docs-navigation`
   - `npm run validate:doc-stale-status`
   - `npm run scan:secrets`
   - `npm run validate:data-leakage`
   - `npm run validate:process-portability`
   - `npm run validate:documentation-methodology`
   - `npm run validate:documentation-core`
   - `npm run validate:documentation-profile`
   - `npm run validate:workflow-state-ledger`
   - `npm run validate:generator-contracts`
   - `npm run validate:schema-coverage`
   - `npm run validate:mutation-guard`

2. Расширенные проверки.
   - `npm run generate:bmc -- --check` только для DataCanvas-профиля или профиля, где BMC — Business Model Canvas, бизнес-модель продукта — включен.
   - `npm test` перед финальной передачей, если изменения затрагивают общие схемы, навигацию, generated artifacts — автоматически создаваемые артефакты, безопасность или процессные контракты.

3. Критерии готовности.
   - Универсальное ядро можно запустить на нейтральной фикстуре вне DataCanvas.
   - DataCanvas подключается через профиль, а не через зашитые правила ядра.
   - Новый документ либо зарегистрирован в навигации, либо добавлен в `ignored_paths` с причиной.
   - Generated artifacts — автоматически создаваемые артефакты — воспроизводимы и не редактируются вручную.
   - Hash manifest — манифест хэшей — поддерживает проверку без записи.
   - Mutation guard — защита от лишних изменений — блокирует неожиданные изменения.
   - Состояние запуска, журнал, очередь решений и записи принятия валидируются схемами.
   - Продуктовые, процессные и архитектурные решения разделены.
   - Публичная навигация не раскрывает sensitive/confidential data — чувствительные или конфиденциальные данные.
   - Полный рабочий процесс можно многократно запускать с сохранением `run_id`, evidence — проверочных свидетельств — и следующего безопасного шага.

## 10. Принятые Допущения

1. DataCanvas остается пилотным ИТ-продуктом для проверки методики, но не является частью универсального ядра.
2. Семантические каскадные правки не применяются автоматически без принятого решения владельца.
3. `CO-*` — изменения продукта, `PROC-*` — изменения процесса, и `ADR-*` — архитектурные решения сохраняют разные контуры полномочий.
4. Generated artifacts — автоматически создаваемые артефакты — обновляются только генераторами.
5. Если профиль нового ИТ-продукта не определяет источник истины, проверка должна блокировать смысловую правку, а не делать вывод по косвенным данным.
