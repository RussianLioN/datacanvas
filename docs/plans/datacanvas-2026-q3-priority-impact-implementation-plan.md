# План Проверки И Применения Смены Приоритетов На 3-Й Квартал По Графу Влияния

Дата: 2026-07-02
Проверка: `npm run validate:product-change-orders`, `npm run validate:change-impact`, `npm run validate:cascading-governance`, `npm run validate:docs-navigation`, `npm run validate:artifact-registry`, `npm run validate:artifact-hashes`
Источник: пользовательское решение сохранить план проверки и применения смены приоритетов на 3-й квартал как отслеживаемый артефакт.

## Кратко

Цель: проверить и, только после подтвержденных решений, применить смену приоритетов на 3-й квартал по заявке `CO-2026-001`: раньше поддержать вызов DataCanvas другими агентами.

Пояснения:

- `CO` - заявка на изменение.
- `A2A` - взаимодействие "агент-агент", то есть вызов DataCanvas другим агентом.
- `BMC` - канва бизнес-модели.
- `BT` - бизнес-требование.
- `NFR` - нефункциональное требование.
- `PBI` - элемент продуктового списка работ.
- `ПШЕ` - оценка трудозатрат в человеко-днях.

Главное правило: не проходить все документы сверху вниз автоматически. Начинать от изменяемого артефакта и идти по графу связей вверх, вниз, в сторону или локально только там, где есть возможное влияние.

Для `CO-2026-001` использовать полный маршрут проверки, потому что это смена квартального приоритета, а не мелкая правка.

## Правила Проверки Влияния

- Локальный маршрут применять для опечаток, ссылок, оформления и уточнений без изменения смысла. Проверять только сам документ, ссылки, навигацию и производные файлы.
- Восходящий маршрут применять, если изменение истории, задачи или требования может затронуть цель продукта, пользователя, ценность, канал, срок, риск или границу доверия.
- Нисходящий маршрут применять, если меняется видение продукта, канва бизнес-модели, требование, правило безопасности, процессное правило, срок или приоритет.
- Боковой маршрут применять, если изменение затрагивает соседние артефакты: требования и критерии приемки, истории и список работ, список работ и дорожную карту, дорожную карту и емкость, входной договор и безопасность.
- Полный маршрут применять для смены квартального состава работ, емкости, канала результата, архитектурной границы или доверительной границы.
- Для каждой проверенной связи фиксировать одно состояние: нужна правка, правка не нужна с причиной, или правка заблокирована решением.
- Ветку проверки останавливать, если связь проверена, влияния нет, причина записана и нет признаков дальнейшего смыслового влияния.

## Решения Перед Применением

- Не менять канонический порядок работ, сроки и переносы, пока владелец продукта явно не примет `CO-2026-001`.
- Не утверждать состав 3-го квартала, пока не заполнены емкость команды, резерв, ограничения, уже обещанные работы и источник этих данных.
- Не переносить истории из более позднего периода в 3-й квартал без подтвержденного списка этих историй.
- Не вытеснять истории из 3-го квартала без правила выбора: что переносится, почему и в какой период.
- Не закрывать план, пока не выбран канал результата: Лиса, электронная почта, обратный вызов или согласованное сочетание.
- Не считать сценарий вызова другим агентом готовым к приоритетной реализации без подтвержденного плана отката.
- Если `PROC-038` должен стать обязательным правилом процесса, владелец процесса принимает его отдельным решением.

## Изменения В Артефактах

- Создать отдельный запуск проверки для `CO-2026-001` в каталоге каскадного ведения документации.
- В запросе на изменение указать исходную точку: `docs/product/change-orders/co-2026-001-a2a-first-priority.json`, период `2026-Q3`, затронутые истории `DC-ST-*` и статус решения владельца продукта.
- В отчете влияния записать проверенные связи: вверх, вниз, в сторону и локально.
- В очереди решений зафиксировать открытые решения: принять или отклонить `CO-2026-001`, подтвердить емкость, выбрать канал результата, подтвердить откат, отдельно решить судьбу `PROC-038`.
- В плане емкости 3-го квартала заполнять значения только при подтвержденном источнике. Без источника оставить состояние `pending_external`.
- В отчете перепланирования заполнить таблицу: что уже было в 3-м квартале, что добавляется, что вытесняется, оценка в ПШЕ, причина, новый период, владелец решения.
- Если `CO-2026-001` не принят, сроки, приоритеты и переносы не применять; оставить только проверку влияния и список решений.
- Если `CO-2026-001` принят, обновить список работ, каталог историй, дорожную карту, требования, критерии приемки, матрицу связей, план емкости и отчет перепланирования.
- Производные файлы, навигацию, хеши и артефакты канвы бизнес-модели обновлять только генераторами.

## Перепланирование 3-Го Квартала

- Собрать входные данные: доступная емкость, резерв, отсутствия и ограничения, уже обещанные работы, оценки историй, источник подтверждения.
- Посчитать доступную емкость как емкость команды минус резерв и подтвержденные ограничения.
- Сравнить доступную емкость с текущими и добавляемыми работами.
- Отдельно показать истории, которые поднимаются в 3-й квартал из более позднего периода.
- Отдельно показать истории, которые вытесняются из 3-го квартала, с новым целевым периодом и причиной переноса.
- Если работ больше, чем доступной емкости, подготовить варианты решения: перенести менее важные истории, уменьшить состав работ, разбить историю, увеличить емкость или оставить изменение заблокированным.
- Не менять оценки, сроки и переносы без решения владельца продукта и подтверждения команды, которая будет выполнять работу.

## Проверка Продукта И Договоров

- Видение продукта проверить только на согласованность: поддерживает ли оно вызов другими агентами и нужно ли уточнять фокус 3-го квартала.
- Канву бизнес-модели проверить по каналам запуска, ключевым действиям, ресурсам, партнерам, затратам и каналу результата.
- Требования проверить по `BT-005`, `BT-006`, `BT-012`, `BT-014` и связанным нефункциональным требованиям, особенно безопасности и трассировке.
- Истории `DC-ST-01` - `DC-ST-22` проверить на новый квартальный порядок: что становится ближе, что остается, что уходит позже.
- Входной договор проверить отдельно: кто вызывает DataCanvas, какие данные передает, как указывается источник, как данные отделяются от инструкций, как запрос связывается с результатом.
- Статус и обратный вызов проверить отдельно: состояния выполнения, ошибки, повторные попытки, безопасный текст ответа и запрет раскрытия чувствительных данных.
- Архитектурное решение создавать только если появляется новый сетевой вызов, новый канал исполнения, расширение разрешенных инструментов или новая граница доверия.

## Проверки

- Заявка и влияние: `npm run validate:product-change-orders`, `npm run validate:change-impact`.
- Каскадное ведение документации: `npm run validate:documentation-change-request`, `npm run validate:artifact-dependency-graph`, `npm run validate:impact-analysis`, `npm run validate:decision-queue`, `npm run validate:capacity-plan`, `npm run validate:reprioritization-impact`, `npm run validate:cascading-governance`.
- Продуктовые связи: `npm run validate:schemas`, `npm run validate:backlog-registry`, `npm run validate:traceability-graph`.
- Требования и договоры: `npm run validate:ba-sa`, `npm run validate:interface-contracts`, `npm run validate:state-model`, `npm run validate:error-taxonomy`.
- Канва бизнес-модели: если исходник изменен, выполнить `npm run generate:bmc`, затем `npm run generate:bmc -- --check` и `npm run validate:bmc`.
- Документация и безопасность: `npm run generate:docs-navigation -- --check`, `npm run validate:doc-links`, `npm run validate:docs-navigation`, `npm run validate:doc-stale-status`, `npm run validate:artifact-registry`, `npm run validate:artifact-hashes`, `npm run scan:secrets`, `npm run validate:data-leakage`.
- Финальная проверка: `npm test`.

## Критерии Завершения

- Для каждого затронутого артефакта указано: правка применена, правка не нужна с причиной, или есть блокирующее решение.
- Если `CO-2026-001` не принят, изменения сроков, приоритетов и переносов не применены.
- Если `CO-2026-001` принят, список работ, истории, дорожная карта, емкость и матрица связей согласованы между собой.
- Все переносы историй имеют идентификатор, причину, оценку, новый целевой период и подтверждение владельца продукта.
- Нет незакрытых блокирующих решений, которые мешают считать задачу завершенной.
- Все производные документы обновлены только генераторами.
- Все профильные проверки прошли или ограничение явно зафиксировано.
